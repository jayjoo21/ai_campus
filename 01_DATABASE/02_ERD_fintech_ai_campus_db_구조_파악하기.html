1-1. ERD를 처음 볼 때는 이 순서로 읽기

ERD(Entity Relationship Diagram)는 테이블 이름을 전부 외우는 그림이 아니라, 어떤 데이터가 있고 그 데이터가 어떻게 연결되는지를 보여주는 설계도입니다. 처음부터 모든 선을 따라가지 말고 아래 순서로 읽으면 훨씬 쉽습니다.

ERD 읽기 5단계
1스키마 찾기큰 업무 영역을 먼저 구분합니다. 이 모델의 중심은 fintech_fraud_lab_class와 stock_data입니다.
2중심 테이블 찾기customers, stocks처럼 여러 테이블이 연결되는 기준점을 찾습니다.
3PK 확인한 행을 유일하게 구분하는 키를 찾습니다. 예: customer_id, transaction_id.
4FK 따라가기다른 테이블의 PK를 참조하는 컬럼을 따라가며 관계를 읽습니다.
5시간·금액·라벨 확인AI 분석에 중요한 시각, 금액, 상태, 정답 라벨 컬럼을 확인합니다.
ERD는 “표의 목록”이 아니라 “업무 데이터가 이동하고 연결되는 지도”라고 생각하면 됩니다.
한 테이블을 볼 때 세 가지 질문
① 한 행은 무엇을 뜻하는가? ② PK는 무엇인가? ③ 어떤 FK로 다른 테이블과 연결되는가? 이 세 질문만 반복해도 ERD 해석 속도가 크게 빨라집니다.

2. DB 초보자가 꼭 알아야 하는 7가지

Schema(스키마)
테이블들을 목적별로 모아 둔 큰 폴더와 비슷합니다.
Table(테이블)
같은 종류의 데이터를 행과 열 형태로 저장한 표입니다.
Row(행)
한 고객, 한 거래, 한 결제처럼 “한 건”의 데이터입니다.
Column(컬럼)
이름, 금액, 시각처럼 각 행이 가진 속성입니다.
PK(Primary Key)
각 행을 절대 겹치지 않게 식별하는 대표 키입니다.
FK(Foreign Key)
다른 테이블의 PK를 가리켜 테이블끼리 연결하는 키입니다.
NULL
0이나 빈 문자열이 아니라 “값이 없거나 아직 모름”을 뜻합니다.
ENUM
미리 정한 후보값 중 하나만 저장하게 제한한 데이터형입니다.
JSON
여러 구조의 세부정보를 {키:값} 형태로 유연하게 담는 데이터형입니다.
초보자 주의: customer_id=1001은 고객의 이름이 아니라 “연결용 번호”입니다. 이름을 알고 싶으면 customers와 JOIN해야 합니다.

JOIN을 한 문장으로 이해하기

SELECT c.name, a.balance
FROM customers c
JOIN accounts a
 ON c.customer_id = a.customer_id;

뜻: customers의 고객번호와 accounts의 고객번호가 같은 행끼리 붙여서 “고객 이름 + 계좌잔액”을 한 화면에서 보겠다는 의미입니다.

JOIN SQL을 읽는 4단계

① SELECT최종적으로 어떤 컬럼을 볼지 정합니다.
② FROM기준이 되는 첫 번째 테이블을 정합니다.
③ JOIN ... ON어떤 키가 같은 행끼리 붙일지 정합니다.
④ WHERE / ORDER BY대상을 좁히고 결과 순서를 정합니다.

4. 데이터형 빠르게 읽는 법

BIGINT / INT
정수. ID, 건수, 연체일수 등에 사용합니다.
DECIMAL(18,2)
소수점 오차가 없어야 하는 금액에 적합합니다. 18자리 중 소수 2자리.
VARCHAR(n) / TEXT
문자열. 짧은 이름은 VARCHAR, 긴 본문은 TEXT 계열을 사용합니다.
DATE / DATETIME / TIMESTAMP
날짜만 / 날짜+시각 / 시스템 시각기록에 자주 쓰는 형식입니다.
CHAR(2), CHAR(3)
KR, US 같은 국가코드나 KRW 같은 고정 길이 코드에 적합합니다.
TINYINT
이 DB에서는 0/1 플래그에 많이 사용합니다. 예: 0=아님, 1=맞음.
ENUM(...)
허용된 코드값 중 하나만 저장하므로 데이터 품질을 유지하기 쉽습니다.
JSON
모델 성능지표·설명값·외부 원문처럼 구조가 유동적인 데이터를 담습니다.

왜 금융 데이터에서는 데이터형이 특히 중요할까?

금액은 FLOAT보다 DECIMAL
금액은 소수점 오차가 누적되면 안 되므로 DECIMAL(18,2)처럼 정확한 십진형을 많이 사용합니다.
날짜와 시각은 문자열로 두지 않기
DATETIME으로 저장하면 기간 필터, 정렬, 시간차 계산을 안정적으로 수행할 수 있습니다.
코드는 길이를 일정하게
KRW, USD 같은 통화코드는 CHAR(3), 국가코드는 CHAR(2)처럼 고정길이를 사용하면 의미가 명확합니다.
JSON은 유연하지만 남용하지 않기
구조가 자주 바뀌는 상세정보에는 유용하지만, 자주 검색·JOIN할 핵심값까지 JSON에 넣으면 분석이 어려워질 수 있습니다.

7. 반드시 짚고 넘어갈 포인트

① PK와 업무번호는 다를 수 있다
내부 PK는 시스템 연결용입니다. 실제 카드번호·계좌번호를 그대로 PK로 쓰지 않는 이유는 보안과 변경 가능성 때문입니다.
② NULL과 0은 다르다
paid_amount=0은 0원을 낸 것이고, paid_at=NULL은 아직 납부시각이 없다는 뜻일 수 있습니다.
③ fraud_label은 Feature가 아니다
학습 시 정답으로 쓰는 컬럼입니다. 예측할 때 이 값을 입력 Feature로 사용하면 데이터 누수(leakage)가 됩니다.
④ 시간 기준을 지켜야 한다
FDS/CSS 모델에서는 예측 시점 이후의 정보가 Feature에 섞이지 않도록 Point-in-Time 기준을 지켜야 합니다.
⑤ 원문과 가공데이터를 구분한다
external_raw_records는 원문, public_* 및 분석 테이블은 가공·정제 결과로 볼 수 있습니다.
⑥ RAG는 문서를 잘게 나눠 검색한다
kind_disclosures 원문을 kind_disclosure_chunks로 나누는 이유가 바로 검색 단위를 만들기 위해서입니다.

ERD와 AI 프로젝트를 연결할 때 추가로 확인할 것

⑦ Grain(행의 단위)을 먼저 정의
customers는 고객 1명, transactions는 거래 1건, stock_prices는 종목·날짜별 가격 1건처럼 “한 행이 무엇인지”가 분석의 출발점입니다.
⑧ 1:N JOIN 후 행이 늘어나는 이유 이해
고객 1명에 거래가 100건이면 JOIN 결과도 100행이 될 수 있습니다. 집계 전에 중복처럼 보이는 행을 무조건 제거하면 안 됩니다.
⑨ 기준시점이 다른 데이터를 바로 합치지 않기
실시간 거래와 일별 시장가격, 월별 거시지표는 시간 단위가 다릅니다. 분석 목적에 맞게 기준시점을 맞춰야 합니다.
⑩ 모델 결과도 데이터로 관리
예측값·모델버전·실행시각을 저장하면 나중에 왜 그런 판단이 나왔는지 재현할 수 있습니다.

  1. customers.customer_id = accounts.customer_id로 JOIN합니다.
