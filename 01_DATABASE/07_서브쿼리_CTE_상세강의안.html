1. 왜 서브쿼리가 필요한가?

SQL을 작성하다 보면 단순한 SELECT → FROM → WHERE만으로는 표현하기 어려운 요구가 생깁니다. 먼저 어떤 데이터를 계산하거나 골라낸 뒤, 그 결과를 다시 다른 조회의 조건이나 입력으로 사용해야 하기 때문입니다.

이 주제에서 확인할 것
무엇을 만들려는가?

한 번의 SELECT만으로는 바로 만들기 어려운 결과를, 먼저 중간 결과를 구한 뒤 다시 사용하는 방식으로 해결합니다.

왜 필요한가?

실제 분석에서는 ‘조건에 맞는 고객을 먼저 찾고, 그 고객의 상세정보를 다시 조회’하는 식의 2단계 사고가 자주 필요합니다.

어떤 데이터를 사용하는가?

customers, card_payments

실행하면 무엇이 보여야 하는가?

고액 승인결제가 있는 고객만 골라 지역·신용점수와 함께 조회되는 결과를 확인합니다.

최종 Grain

최종 결과는 customer_id 기준 고객 1명 = 1행

한 번의 SELECT 안에서 “먼저 찾고 → 그 결과를 다시 사용”해야 할 때 서브쿼리가 자연스럽게 등장합니다.

조건을 먼저 계산할 때

특정 조건을 만족하는 고객 ID를 먼저 구하고, 그 고객만 다시 조회할 수 있습니다.

집계 결과를 다시 필터링할 때

고객별 결제건수를 만든 다음 일정 건수 이상인 고객만 남길 수 있습니다.

행마다 계산값을 붙일 때

고객 한 행에 승인결제 건수처럼 별도로 계산한 값을 붙일 수 있습니다.

2. 서브쿼리는 어떻게 작성하는가?

서브쿼리는 SELECT 문 안에 들어 있는 또 다른 SELECT 문입니다. 괄호 ( ... )로 감싸고, 위치에 따라 역할이 달라집니다.

이 주제에서 확인할 것
무엇을 만들려는가?

서브쿼리가 들어가는 위치에 따라 WHERE용, FROM용, SELECT용으로 역할이 달라지는 것을 구분합니다.

왜 필요한가?

서브쿼리는 단순히 괄호 안에 SELECT를 넣는 문법이 아니라, ‘중간 결과를 어디에서 사용할 것인가’를 결정하는 구조입니다.

어떤 데이터를 사용하는가?

card_payments, customers

실행하면 무엇이 보여야 하는가?

WHERE에서는 고객 목록, FROM에서는 고객별 집계표, SELECT에서는 행마다 붙는 단일 계산값이 만들어지는 차이를 확인합니다.

최종 Grain

서브쿼리 위치에 따라 Grain이 달라지므로 각 예제에서 별도로 확인

WHERE 서브쿼리Filtering Subquery

조건에 사용할 값이나 목록을 만듭니다. IN, EXISTS, 비교연산자와 함께 자주 사용합니다.

FROM 서브쿼리Derived Table

서브쿼리 결과를 임시 테이블처럼 사용합니다. 반드시 별칭을 붙이는 방식이 일반적입니다.

SELECT 서브쿼리Scalar Subquery

각 행에 하나의 계산값을 붙입니다. 반드시 한 행·한 값으로 귀결되어야 합니다.

2-1. FROM 안의 서브쿼리

USE fintech_fraud_lab_class;

SELECT
    customer_id,
    payment_count,
    total_amount
FROM (
    SELECT
        customer_id,
        COUNT(*) AS payment_count,
        SUM(amount) AS total_amount
    FROM card_payments
    WHERE is_approved = 1
    GROUP BY customer_id
) AS payment_summary
WHERE payment_count >= 10
ORDER BY total_amount DESC;
Derived Table
FROM (SELECT ... ) AS payment_summary처럼 FROM 안에서 만든 임시 결과를 파생 테이블이라고 합니다.

2-2. SELECT 안의 서브쿼리

USE fintech_fraud_lab_class;

SELECT
    customer_id,
    region,
    credit_score,
    (
        SELECT COUNT(*)
        FROM card_payments AS cp
        WHERE cp.customer_id = c.customer_id
          AND cp.is_approved = 1
    ) AS approved_payment_count
FROM customers AS c
LIMIT 20;

중첩 서브쿼리의 구조
바깥 SELECT — 최종 결과
중간 SELECT — 고객별 집계
안쪽 SELECT — 승인·기간 필터
괄호가 깊어질수록 데이터가 어느 단계에서 어떻게 바뀌는지 추적하기 어려워집니다.

3. 서브쿼리만으로도 되는데 왜 CTE가 더 필요한가?

서브쿼리는 매우 유용하지만 단계가 많아지면 괄호가 깊어지고, 같은 계산을 여러 곳에서 반복하기 쉬우며, 중간 결과의 의미를 이름으로 표현하기 어렵습니다. CTE는 이 문제를 “단계를 위에서 아래로 이름 붙여 펼치는 방식”으로 해결합니다.

이 주제에서 확인할 것
무엇을 만들려는가?

같은 다단계 처리를 중첩 서브쿼리와 CTE로 각각 작성해 보고, CTE가 왜 읽기 쉽고 관리하기 좋은지 비교합니다.

왜 필요한가?

단계가 많아질수록 중첩 괄호는 데이터 흐름과 Grain 변화를 추적하기 어렵게 만듭니다. CTE는 각 단계에 이름을 붙여 위에서 아래로 읽게 해 줍니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

두 방식이 논리적으로 같은 결과를 만들 수 있지만, CTE 쪽에서는 filtered_payments → customer_summary → 최종 SELECT 흐름이 더 분명하게 보입니다.

최종 Grain

최종 결과는 customer_id 기준 고객 1명 = 1행

중첩 서브쿼리

SELECT
    customer_id,
    payment_count,
    total_amount
FROM (
    SELECT
        customer_id,
        COUNT(*) AS payment_count,
        SUM(amount) AS total_amount
    FROM (
        SELECT
            customer_id,
            amount
        FROM card_payments
        WHERE is_approved = 1
          AND payment_at >= '2026-01-01'
          AND payment_at <  '2026-08-01'
    ) AS filtered_payments
    GROUP BY customer_id
) AS customer_summary
WHERE payment_count >= 10
ORDER BY total_amount DESC;

같은 흐름을 CTE로

WITH filtered_payments AS (
    SELECT
        customer_id,
        amount
    FROM card_payments
    WHERE is_approved = 1
      AND payment_at >= '2026-01-01'
      AND payment_at <  '2026-08-01'
),
customer_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS payment_count,
        SUM(amount) AS total_amount
    FROM filtered_payments
    GROUP BY customer_id
)
SELECT
    customer_id,
    payment_count,
    total_amount
FROM customer_summary
WHERE payment_count >= 10
ORDER BY total_amount DESC;
비교 항목중첩 서브쿼리CTE
읽는 방향안쪽 → 바깥쪽으로 추적위 → 아래 단계 순서
중간 결과 이름별칭은 가능하지만 구조가 깊어짐filtered_payments, customer_summary처럼 역할을 이름으로 표현
재사용같은 논리를 다시 적기 쉬움같은 CTE를 뒤 단계에서 여러 번 참조 가능
디버깅중간 결과만 떼어 확인하기 불편각 CTE의 SELECT를 따로 실행해 확인하기 쉬움
Grain 추적단계가 깊으면 놓치기 쉬움각 CTE마다 Grain을 명시하기 쉬움
긴 Snapshot SQL괄호 구조가 복잡해짐계좌·대출·거래·동의 등을 역할별 CTE로 분리 가능
CTE가 복잡한 SQL을 정리하는 방식
CTE 1 · 필터필요한 기간과 대상만 남김
CTE 2 · 집계원하는 Grain으로 요약
최종 SELECT필요한 결과만 조합
CTE의 핵심은 무조건 성능을 높이는 것이 아니라, 복잡한 SQL의 데이터 흐름과 중간 결과를 명확하게 표현하는 데 있습니다.
CTE = 자동 성능 향상 기능은 아닙니다.
DBMS와 쿼리 형태에 따라 실행계획은 달라질 수 있습니다. CTE를 사용하는 가장 확실한 이유는 가독성, 단계 분리, 재사용, Grain 관리, 검증 용이성입니다.

4. CTE 단원에서 자주 등장하는 용어

CTECommon Table Expression

한 SQL 문 안에서 이름을 붙여 사용하는 중간 결과입니다.

Grain한 행의 단위

결과 한 행이 정확히 무엇을 의미하는지 나타냅니다. 예: 결제 1건, 고객 1명, 실험 배정 1건.

Aggregation집계

여러 행을 COUNT, SUM, AVG 등으로 요약하는 작업입니다.

Pre-aggregation사전 집계

JOIN 전에 N쪽 데이터를 원하는 Grain으로 먼저 집계하는 방법입니다.

Fan-out행 증폭

여러 1:N 테이블을 동시에 JOIN하면서 조합 수만큼 행이 복제되는 현상입니다.

Snapshot시점 상태값

특정 기준시점에 존재했던 고객·계좌·대출 등의 상태를 한 행에 정리한 데이터입니다.

Point-in-Time시점 정합성

판단 시점 이후에 생긴 미래 정보를 사용하지 않는 원칙입니다.

Data Leakage정보 누수

예측 시점에는 알 수 없었던 미래·사후 정보를 학습 데이터에 포함하는 오류입니다.

COALESCENULL 대체

여러 값 중 첫 번째 NULL이 아닌 값을 반환합니다. 예: COALESCE(account_count,0).

5. CTE 기본 문법 — WITH → AS → 최종 SELECT

CTE(Common Table Expression)는 한 SQL 문에서 사용할 이름 붙은 중간 결과입니다. 실제 테이블을 새로 생성하는 것이 아니라 현재 SQL 문 안에서만 사용할 논리적 결과입니다.

이 주제에서 확인할 것
무엇을 만들려는가?

CTE의 가장 기본적인 형태인 WITH → AS (...) → 최종 SELECT 구조를 익힙니다.

왜 필요한가?

긴 SQL을 여러 단계로 나누기 전에, 우선 하나의 중간 결과에 이름을 붙이고 다시 조회하는 가장 단순한 패턴을 이해해야 합니다.

어떤 데이터를 사용하는가?

stock_data.stock_prices

실행하면 무엇이 보여야 하는가?

삼성전자(005930)의 거래일별 종가가 날짜순으로 조회되고, CTE를 사용하지 않았을 때와 결과 자체는 같음을 확인합니다.

최종 Grain

stock_code × trade_date 1행

-- CTE의 가장 기본적인 문법 형태
WITH cte_name AS (               -- ① cte_name이라는 중간 결과에 이름을 붙입니다.
    SELECT ...                   -- ② 필요한 컬럼을 선택합니다.
    FROM ...                     -- ③ 원천 테이블을 지정합니다.
    WHERE ...                    -- ④ 필요한 행만 필터링합니다.
)
SELECT ...                       -- ⑤ CTE에서 최종적으로 반환할 컬럼을 선택합니다.
FROM cte_name;                   -- ⑥ CTE를 일반 테이블처럼 조회합니다.

5-1. 가장 짧은 CTE

USE stock_data;  -- 실제 주가 테이블이 있는 DB를 선택합니다.
--
-- ① 삼성전자 주가만 담은 가장 단순한 CTE를 만듭니다.
WITH samsung_prices AS (
    SELECT
        stock_code,              -- 종목코드
        trade_date,              -- 거래일
        close_price              -- 종가
    FROM stock_prices            -- 일별 OHLCV가 저장된 원천 테이블
    WHERE stock_code = '005930'  -- 삼성전자(005930)만 남깁니다.
)
-- ② 위에서 만든 CTE를 일반 테이블처럼 조회합니다.
SELECT
    stock_code,
    trade_date,
    close_price
FROM samsung_prices
ORDER BY trade_date              -- 과거 → 최신 순서로 정렬합니다.
LIMIT 10;                        -- 결과를 10행만 확인합니다.
중간 결과samsung_prices라는 이름으로 삼성전자 행만 준비합니다.
Grainstock_code × trade_date 1행입니다. CTE를 쓴다고 Grain이 자동으로 바뀌지 않습니다.

6. 필터 CTE — 필요한 행을 먼저 줄이기

뒤에서 JOIN이나 집계를 하기 전에 기간·승인여부처럼 명확한 조건을 먼저 적용하면 다음 단계가 단순해집니다.

이 주제에서 확인할 것
무엇을 만들려는가?

승인된 결제 중 특정 기간에 해당하는 행만 먼저 골라 다음 단계에서 사용할 정리된 원천 데이터를 만듭니다.

왜 필요한가?

뒤에서 JOIN이나 GROUP BY를 하기 전에 분석 대상이 아닌 행을 먼저 줄이면 쿼리의 의미가 명확해지고 다음 단계가 단순해집니다.

어떤 데이터를 사용하는가?

fintech_fraud_lab_class.card_payments

실행하면 무엇이 보여야 하는가?

승인된 결제 중 2026-01-01 이상, 2026-08-01 미만의 결제만 시간순으로 보입니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;  -- FDS·CSS·개인화 데이터가 있는 금융 DB를 선택합니다.
--
-- ① 먼저 분석 대상이 되는 결제만 남기는 필터 CTE를 만듭니다.
WITH recent_approved_payments AS (
    SELECT
        payment_id,              -- 결제 1건을 구분하는 PK
        customer_id,             -- 결제 고객 ID
        payment_at,              -- 결제 발생 시각
        amount,                  -- 결제 금액
        fraud_label              -- 정상/사기 Target. 모델 Feature로 쓰지 않습니다.
    FROM card_payments           -- FDS의 기준 Grain이 되는 결제 원천 테이블
    WHERE is_approved = 1        -- 승인된 결제만 학습 후보로 남깁니다.
      AND payment_at >= '2026-01-01'  -- 분석 시작시점 포함
      AND payment_at <  '2026-08-01'  -- 분석 종료시점 미포함: [시작, 종료) 방식
)
-- ② 필터된 CTE 결과를 시간순으로 확인합니다.
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    fraud_label
FROM recent_approved_payments
ORDER BY payment_at              -- 결제 발생 순서대로 확인합니다.
LIMIT 100;                       -- 결과를 100행만 확인합니다.
Grain 변화 없음
필터는 행의 개수만 줄일 뿐 한 행이 “결제 1건”이라는 의미는 그대로 유지됩니다.
필터 CTE의 역할
전체 결제많은 행
→
승인 여부is_approved = 1
→
기간[시작, 종료)
→
정리된 원천다음 CTE 입력

7. 집계 CTE — 여러 결제를 고객 1행으로 바꾸기

첫 CTE가 결제 1건 Grain이라면, 두 번째 CTE에서 GROUP BY customer_id를 사용해 고객 1명 Grain으로 바꿀 수 있습니다.

이 주제에서 확인할 것
무엇을 만들려는가?

결제 1건 단위 데이터를 고객별로 묶어 고객 1명당 결제 건수·합계·평균·최근 결제시각을 만듭니다.

왜 필요한가?

모델이나 고객 단위 분석에는 거래 수천 행을 그대로 쓰기보다 고객별 요약값이 필요합니다. 이때 GROUP BY가 Grain을 바꿉니다.

어떤 데이터를 사용하는가?

recent_approved_payments CTE

실행하면 무엇이 보여야 하는가?

고객별로 한 행이 나오고, 결제 건수·총 결제금액·평균 결제금액·최근 결제시각이 함께 표시됩니다.

최종 Grain

payment_id Grain → customer_id Grain으로 변경

USE fintech_fraud_lab_class;  -- 금융 AI 실습 DB 선택
--
-- ① 1단계: 승인된 결제 중 필요한 기간만 먼저 줄입니다.
WITH recent_approved_payments AS (
    SELECT
        payment_id,              -- 결제 식별자
        customer_id,             -- 고객 식별자
        payment_at,              -- 결제 시각
        amount,                  -- 결제 금액
        fraud_label              -- Target 확인용 컬럼
    FROM card_payments
    WHERE is_approved = 1
      AND payment_at >= '2026-01-01'
      AND payment_at <  '2026-08-01'
),
-- ② 2단계: 1단계 결과를 고객별 1행으로 집계합니다.
customer_summary AS (
    SELECT
        customer_id,                         -- GROUP BY 기준: 고객 1명
        COUNT(*) AS `payment_count`,         -- 고객별 승인 결제 건수
        SUM(amount) AS `total_amount`,       -- 고객별 총 결제금액
        AVG(amount) AS `avg_amount`,         -- 고객별 평균 결제금액
        MAX(payment_at) AS `latest_payment_at` -- 고객의 가장 최근 결제시각
    FROM recent_approved_payments            -- 원본이 아니라 1단계 CTE를 입력으로 사용
    GROUP BY customer_id                     -- 결과 Grain을 고객 1명 = 1행으로 변경
)
-- ③ 최종적으로 고객별 요약 결과를 조회합니다.
SELECT
    customer_id,
    payment_count,
    total_amount,
    avg_amount,
    latest_payment_at
FROM customer_summary
ORDER BY payment_count DESC      -- 결제 건수가 많은 고객부터 확인
LIMIT 20;                        -- 상위 20명만 출력
GROUP BY가 Grain을 바꾸는 과정
payment_id결제 1건 = 1행
→
GROUP BYcustomer_id
→
customer_id고객 1명 = 1행
핵심
CTE를 읽을 때는 각 단계마다 입력 Grain → 처리 → 출력 Grain을 확인하면 긴 SQL도 구조가 보입니다.

8. 다중 CTE — 역할별로 나누고 마지막에 결합하기

CTE가 여러 개일 때는 각 CTE에 한 가지 역할을 부여합니다. 원천 선택, 집계, 마스터 준비, 최종 JOIN처럼 단계가 분리되면 수정 지점도 명확해집니다.

이 주제에서 확인할 것
무엇을 만들려는가?

하나의 긴 SQL을 결제 필터 → 고객별 집계 → 고객 마스터 → 최종 JOIN으로 역할별 분리합니다.

왜 필요한가?

업무 로직이 늘어날수록 한 SELECT 안에 모든 처리를 넣으면 수정과 검증이 어렵습니다. CTE별 역할을 하나씩 부여하면 구조가 선명해집니다.

어떤 데이터를 사용하는가?

card_payments, customers

실행하면 무엇이 보여야 하는가?

고객 1명당 한 행이 나오고, 지역·소득구간·위험등급과 승인결제 요약값이 한 행에 함께 붙습니다.

최종 Grain

customer_id 1명 = 1행

USE fintech_fraud_lab_class;  -- 금융 AI 실습 DB 선택
--
-- ① 승인된 결제만 남깁니다.
WITH approved_payments AS (
    SELECT
        payment_id,
        customer_id,
        merchant_id,
        amount
    FROM card_payments
    WHERE is_approved = 1        -- 승인 결제만 사용
),
-- ② 승인 결제를 고객 단위로 먼저 집계합니다.
customer_payment AS (
    SELECT
        customer_id,
        COUNT(*) AS `payment_count`,   -- 고객별 결제 건수
        SUM(amount) AS `total_amount`  -- 고객별 총 결제금액
    FROM approved_payments
    GROUP BY customer_id               -- 고객 1명 = 1행으로 축약
),
-- ③ 고객 마스터에서 설명 변수만 따로 준비합니다.
customer_master AS (
    SELECT
        customer_id,
        region,
        income_band,
        risk_segment
    FROM customers
)
-- ④ 고객 마스터를 기준으로 결제 요약을 붙입니다.
SELECT
    c.customer_id,
    c.region,
    c.income_band,
    c.risk_segment,
    p.payment_count,
    p.total_amount
FROM customer_master AS c
LEFT JOIN customer_payment AS p
  ON c.customer_id = p.customer_id  -- 동일 고객끼리 연결
-- LEFT JOIN이므로 결제가 없는 고객도 고객 행 자체는 남을 수 있습니다.
ORDER BY p.total_amount DESC
LIMIT 50;
1 · approved_payments승인된 결제만 선택
2 · customer_payment고객별 결제 요약
3 · customer_master고객 설명정보 준비
4 · 최종 SELECT고객 기준으로 결합
다중 CTE의 좋은 이름
data1, temp2보다 approved_payments, customer_payment처럼 중간 결과의 의미를 드러내는 이름이 좋습니다.

9. CTE가 특히 유용한 이유 — Fan-out을 사전 집계로 막기

Fan-out은 한 고객에게 계좌도 여러 개이고 거래도 여러 건일 때, 두 1:N 테이블을 그대로 붙여 가능한 조합만큼 행이 늘어나는 현상입니다.

이 주제에서 확인할 것
무엇을 만들려는가?

계좌와 거래처럼 고객당 여러 행이 있는 테이블을 그대로 JOIN할 때 발생하는 Fan-out을 확인하고, 사전 집계로 해결합니다.

왜 필요한가?

Fan-out을 이해하지 못하면 거래금액이나 잔액이 중복 합산되어 실제보다 훨씬 큰 값이 만들어질 수 있습니다.

어떤 데이터를 사용하는가?

customers, accounts, transactions

실행하면 무엇이 보여야 하는가?

위험한 JOIN에서는 고객 한 명이 여러 행으로 반복되고, 사전 집계 후 JOIN에서는 다시 고객 1명당 1행으로 정리되는 차이를 확인합니다.

최종 Grain

최종 목표는 customer_id 1명 = 1행

Fan-out 예
고객 1명기준 1행
계좌 2개accounts 2행
거래 10건transactions 10행
직접 JOIN하면
계좌 2개 × 거래 10건 = 최대 20개 조합이 만들어질 수 있습니다.

9-1. 위험한 JOIN

USE fintech_fraud_lab_class;  -- 금융 AI 실습 DB 선택
--
-- =========================================================
-- [의도적으로 위험한 예제]
-- 고객 한 명에게 계좌가 여러 개이고 거래도 여러 건이면
-- accounts × transactions 조합만큼 행이 늘어날 수 있습니다.
-- =========================================================
SELECT
    c.customer_id,               -- 기준 고객
    a.account_id,                -- 고객이 가진 계좌
    t.transaction_id             -- 고객의 거래
FROM customers AS c              -- 고객 1행을 기준으로 시작
LEFT JOIN accounts AS a
  ON c.customer_id = a.customer_id   -- 고객 1 : 계좌 N
LEFT JOIN transactions AS t
  ON c.customer_id = t.customer_id   -- 고객 1 : 거래 N
WHERE c.customer_id = 1;         -- 고객 1명만 보며 Fan-out을 관찰
--
-- 예: 계좌 2개 × 거래 10건이면 최대 20행으로 늘어날 수 있습니다.
-- 따라서 이 결과를 '고객 1명 = 1행' 데이터로 착각하면 안 됩니다.

9-2. 해결: 각 테이블을 먼저 고객 1행으로 집계

USE fintech_fraud_lab_class;  -- 금융 AI 실습 DB 선택
--
-- ① 계좌 원천을 먼저 고객 단위로 집계합니다.
--    이렇게 하면 accounts의 여러 행이 고객별 1행으로 축약됩니다.
WITH account_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS `account_count`,      -- 고객이 가진 계좌 수
        SUM(balance) AS `total_balance`   -- 고객의 전체 계좌 잔액 합계
    FROM accounts
    GROUP BY customer_id                  -- 고객 1명 = 1행
),
-- ② 거래 원천도 별도로 고객 단위로 집계합니다.
transaction_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS `transaction_count`,          -- 고객별 거래 건수
        SUM(amount) AS `total_transaction_amount` -- 고객별 거래금액 합계
    FROM transactions
    GROUP BY customer_id                          -- 고객 1명 = 1행
)
-- ③ 두 개의 '고객별 1행' 요약 결과를 고객 마스터에 붙입니다.
SELECT
    c.customer_id,
    c.region,
    a.account_count,
    a.total_balance,
    t.transaction_count,
    t.total_transaction_amount
FROM customers AS c
LEFT JOIN account_summary AS a
  ON c.customer_id = a.customer_id        -- 고객 1 : 요약 1
LEFT JOIN transaction_summary AS t
  ON c.customer_id = t.customer_id        -- 고객 1 : 요약 1
WHERE c.customer_id = 1;
--
-- 핵심: 원천 1:N 테이블끼리 직접 JOIN하지 않고
--       각각 먼저 집계한 뒤 연결하면 Fan-out을 막을 수 있습니다.
Pre-aggregation(사전 집계)
accounts N행고객별 여러 계좌
→
account_summary고객별 1행
→
customersN:1로 안전하게 결합
Pre-aggregation
JOIN하기 전에 N쪽 원천을 원하는 기준키로 먼저 요약하는 방법입니다. CTE는 이 중간 요약 결과에 이름을 붙이기 좋기 때문에 Fan-out 방지 패턴과 잘 맞습니다.

10. Point-in-Time Snapshot — 배정 시점에 존재했던 정보만 사용하기

캠페인 배정 1건을 기준으로 금융 상태를 만들 때는 현재 계좌나 현재 대출을 그대로 붙이면 안 됩니다. 배정 당시 이미 존재했던 정보만 사용해야 합니다.

이 주제에서 확인할 것
무엇을 만들려는가?

캠페인을 배정한 바로 그 시점에 고객이 보유하고 있던 계좌 정보를 모아 배정시점 Customer Snapshot을 만듭니다.

왜 필요한가?

개인화 모델은 캠페인 배정 당시 알 수 있었던 정보로만 판단해야 합니다. 배정 이후 새로 생긴 계좌를 포함하면 미래정보 누수가 발생합니다.

어떤 데이터를 사용하는가?

campaign_experiments, accounts

실행하면 무엇이 보여야 하는가?

각 experiment_id마다 한 행이 나오고, assigned_at 이전에 개설된 계좌 수와 활성계좌 잔액만 붙습니다.

최종 Grain

experiment_id 1건 = 1행

Point-in-Time을 시간축으로 이해하기
배정 이전계좌 개설
사용 가능
배정 이전거래 발생
사용 가능
assigned_at캠페인 배정
기준시점
배정 이후새 계좌·거래
미래 정보 → 제외
USE fintech_fraud_lab_class;  -- 개인화 실습 데이터가 있는 금융 DB 선택
--
-- ① ce: 캠페인 배정 이벤트를 기준 데이터로 준비합니다.
--    최종 Grain은 experiment_id 1건 = 1행입니다.
WITH ce AS (
    SELECT
        experiment_id,            -- 캠페인/실험 배정 건의 PK
        customer_id,              -- 배정 대상 고객
        assigned_at,              -- 매우 중요: 이 시점을 기준으로 과거 정보만 사용
        campaign_name,            -- 어떤 캠페인을 배정했는지
        converted                 -- 전환 여부(Target/성과 확인용)
    FROM campaign_experiments
    ORDER BY assigned_at
    LIMIT 30000                   -- 처리량을 고려해 최대 3만 건 제한
),
-- ② acct: 각 experiment의 배정시점까지 존재했던 계좌만 집계합니다.
acct AS (
    SELECT
        ce.experiment_id,
        COUNT(DISTINCT a.account_id) AS `account_count`, -- 중복을 피하며 계좌 수 계산
        SUM(
            CASE
                WHEN a.status = 'ACTIVE' THEN a.balance -- 활성계좌 잔액만 합산
                ELSE 0
            END
        ) AS `active_balance`
    FROM ce
    LEFT JOIN accounts AS a
      ON a.customer_id = ce.customer_id   -- 같은 고객의 계좌 연결
     AND a.opened_at <= ce.assigned_at    -- 배정 이후 개설 계좌는 미래정보이므로 제외
    GROUP BY ce.experiment_id              -- 다시 experiment 1건 = 1행으로 집계
)
-- ③ 기준 ce에 계좌 Snapshot을 붙여 최종 결과를 만듭니다.
SELECT
    ce.experiment_id,
    ce.customer_id,
    ce.assigned_at,
    ce.campaign_name,
    acct.account_count,
    acct.active_balance,
    ce.converted
FROM ce
LEFT JOIN acct
  ON acct.experiment_id = ce.experiment_id -- experiment_id로 1:1에 가깝게 결합
ORDER BY ce.assigned_at;                   -- 배정시간 순서로 확인
Snapshot
특정 기준시점의 고객 상태를 한 행으로 정리한 데이터입니다. 여기서는 experiment_id 하나가 최종 한 행의 기준입니다.

11. 동의정보도 현재 상태가 아니라 기준시점 상태로 보기

동의 이력은 단순 현재값이 아닙니다. 배정 시점 이전에 동의가 부여되었고, 그 시점까지 철회되지 않았는지를 함께 확인해야 합니다.

이 주제에서 확인할 것
무엇을 만들려는가?

캠페인 배정 당시 AI_PROFILING 동의가 실제로 유효했는지를 실험 건별 0/1 값으로 만듭니다.

왜 필요한가?

현재 동의 상태만 보면 과거 시점의 적법한 데이터 사용 여부를 판단할 수 없습니다. 부여시점과 철회시점을 배정시점과 함께 비교해야 합니다.

어떤 데이터를 사용하는가?

campaign_experiments, consent_records

실행하면 무엇이 보여야 하는가?

각 experiment_id마다 한 행이 나오고, 배정 당시 유효한 동의가 있으면 1, 아니면 0이 표시됩니다.

최종 Grain

experiment_id 1건 = 1행

USE fintech_fraud_lab_class;  -- 개인화 실습 DB 선택
--
-- ① 캠페인 배정 시점을 기준축으로 준비합니다.
WITH ce AS (
    SELECT
        experiment_id,
        customer_id,
        assigned_at
    FROM campaign_experiments
    ORDER BY assigned_at
    LIMIT 30000
),
-- ② 각 배정시점에 AI_PROFILING 동의가 유효했는지 계산합니다.
consent AS (
    SELECT
        ce.experiment_id,
        MAX(  -- 동의 레코드가 여러 개여도 하나라도 유효하면 1이 되도록 MAX 사용
            CASE
                WHEN cr.consent_type = 'AI_PROFILING'   -- AI Profiling 동의 유형만 확인
                 AND cr.consent_status = 'GRANTED'      -- 동의 상태가 승인(GRANTED)이고
                 AND cr.granted_at <= ce.assigned_at    -- 동의 시점이 캠페인 배정보다 빠르며
                 AND (
                     cr.revoked_at IS NULL               -- 아직 철회되지 않았거나
                     OR cr.revoked_at > ce.assigned_at   -- 철회가 배정 이후라면 당시에는 유효
                 )
                THEN 1                                   -- 배정 당시 유효한 동의
                ELSE 0                                   -- 유효한 동의가 아님
            END
        ) AS `ai_profiling_granted`
    FROM ce
    LEFT JOIN consent_records AS cr
      ON cr.customer_id = ce.customer_id  -- 같은 고객의 동의 이력 전체를 후보로 연결
    GROUP BY ce.experiment_id             -- experiment 1건당 동의 상태 1개로 축약
)
-- ③ 각 실험별 동의 여부를 확인합니다.
SELECT
    experiment_id,
    ai_profiling_granted
FROM consent
ORDER BY experiment_id;

12. 전체형 CTE — 캠페인 배정시점 Customer 360 Snapshot

이 쿼리는 여러 테이블의 데이터를 단순히 한 번에 조회하기 위한 것이 아니라, 캠페인을 배정한 당시의 고객 금융상태를 다시 재현해 실험 1건당 한 행으로 만드는 것이 핵심입니다. 따라서 먼저 최종 결과에서 무엇을 얻으려는지 확인한 뒤, 각 CTE가 그 결과의 어느 부분을 만드는지 순서대로 읽습니다.

이 쿼리를 작성하는 목적
무엇을 만들려는가?

캠페인 배정 1건마다, 그 배정 시점에 실제로 알 수 있었던 고객의 금융상태를 한 행으로 모은 Customer 360 Snapshot을 만드는 것이 목적입니다. 이 결과가 이후 개인화 추천·Propensity Model·Next-Best-Action 모델에 들어갈 수 있는 학습용 원천 데이터가 됩니다.

왜 필요한가?

캠페인을 받은 고객의 현재 상태를 쓰는 것이 아니라, 배정 당시 상태를 재현해야 공정한 모델 학습이 가능합니다. 계좌·대출·최근 거래·동의정보가 서로 다른 테이블에 흩어져 있으므로, 각 영역을 CTE로 따로 계산한 뒤 experiment_id를 기준으로 한 행에 결합합니다.

어떤 데이터를 사용하는가?

campaign_experiments를 기준축으로 사용하고, accounts, loans, transactions, consent_records를 연결합니다.

실행하면 무엇이 보여야 하는가?

최종 결과 한 행에는 캠페인 정보와 함께 계좌 수·활성잔액·대출 수·활성 대출원금·최대 연체일수·최근 90일 유입/유출금액·AI 프로파일링 동의 여부가 함께 표시되어야 합니다. 또한 모든 값은 assigned_at 시점 이후의 정보를 포함하지 않아야 합니다.

최종 Grain

experiment_id 1건 = 1행

USE fintech_fraud_lab_class;  -- 개인화/Customer 360 실습 DB 선택
--
-- =========================================================
-- [최종형] 캠페인 배정시점 기준 Customer 360 Snapshot
-- 핵심 원칙: assigned_at 이후의 정보는 절대 사용하지 않습니다.
-- 최종 Grain: experiment_id 1건 = 1행
-- =========================================================
--
-- ① ce: 캠페인 배정 이벤트를 기준축으로 준비합니다.
WITH ce AS (
    SELECT
        experiment_id,            -- 실험 배정 건의 PK
        customer_id,              -- 고객 ID
        campaign_name,            -- 캠페인명
        group_name,               -- 실험군/대조군 등 그룹
        assigned_at,              -- Point-in-Time 기준시점
        exposed,                  -- 노출 여부
        clicked,                  -- 클릭 여부
        converted,                -- 전환 여부: 이후 모델의 Target 후보
        revenue_amount            -- 전환 후 매출 성과
    FROM campaign_experiments
    ORDER BY assigned_at
    LIMIT 30000                   -- 처리량을 제한
),
--
-- ② acct: 배정시점까지 개설된 계좌를 experiment 단위로 집계합니다.
acct AS (
    SELECT
        ce.experiment_id,
        COUNT(DISTINCT a.account_id) AS `account_count`,
        SUM(
            CASE
                WHEN a.status = 'ACTIVE' THEN a.balance -- 현재 활성계좌 잔액만 합산
                ELSE 0
            END
        ) AS `active_balance`
    FROM ce
    LEFT JOIN accounts AS a
      ON a.customer_id = ce.customer_id
     AND a.opened_at <= ce.assigned_at      -- 미래에 개설된 계좌는 제외
    GROUP BY ce.experiment_id
),
--
-- ③ loan: 배정시점까지 실행된 대출을 experiment 단위로 집계합니다.
loan AS (
    SELECT
        ce.experiment_id,
        COUNT(DISTINCT l.loan_id) AS `loan_count`,
        SUM(
            CASE
                WHEN l.status IN ('ACTIVE', 'RESTRUCTURED')
                THEN l.principal                  -- 활성/재조정 대출 원금만 합산
                ELSE 0
            END
        ) AS `active_loan_principal`,
        MAX(
            CASE
                WHEN l.overdue_days > 0 THEN l.overdue_days
                ELSE 0
            END
        ) AS `max_overdue_days`                    -- 가장 큰 연체일수
    FROM ce
    LEFT JOIN loans AS l
      ON l.customer_id = ce.customer_id
     AND l.opened_at <= ce.assigned_at             -- 배정 이후 대출은 제외
    GROUP BY ce.experiment_id
),
--
-- ④ txn: 배정 직전 90일 거래만 집계합니다.
txn AS (
    SELECT
        ce.experiment_id,
        COUNT(t.transaction_id) AS `txn_90d`,       -- 최근 90일 거래 건수
        SUM(
            CASE
                WHEN t.transaction_type IN ('DEPOSIT', 'TRANSFER_IN', 'INTEREST')
                THEN t.amount                       -- 유입 거래금액
                ELSE 0
            END
        ) AS `inflow_90d`,
        SUM(
            CASE
                WHEN t.transaction_type IN ('WITHDRAWAL', 'TRANSFER_OUT', 'FEE')
                THEN t.amount                       -- 유출 거래금액
                ELSE 0
            END
        ) AS `outflow_90d`
    FROM ce
    LEFT JOIN transactions AS t
      ON t.customer_id = ce.customer_id
     AND t.transaction_at < ce.assigned_at         -- 배정시점 이후 거래는 미래정보이므로 제외
     AND t.transaction_at >= DATE_SUB(
         ce.assigned_at, INTERVAL 90 DAY            -- 배정시점에서 정확히 90일 전부터
     )
    GROUP BY ce.experiment_id
),
--
-- ⑤ consent: 배정 당시 AI_PROFILING 동의가 유효했는지 확인합니다.
consent AS (
    SELECT
        ce.experiment_id,
        MAX(
            CASE
                WHEN cr.consent_type = 'AI_PROFILING'
                 AND cr.consent_status = 'GRANTED'
                 AND cr.granted_at <= ce.assigned_at
                 AND (
                     cr.revoked_at IS NULL
                     OR cr.revoked_at > ce.assigned_at
                 )
                THEN 1
                ELSE 0
            END
        ) AS `ai_profiling_granted`
    FROM ce
    LEFT JOIN consent_records AS cr
      ON cr.customer_id = ce.customer_id
    GROUP BY ce.experiment_id
)
--
-- ⑥ 최종 SELECT: 모든 Snapshot을 experiment_id 기준으로 결합합니다.
SELECT
    ce.experiment_id,
    ce.customer_id,
    ce.campaign_name,
    ce.group_name,
    ce.assigned_at,
    ce.exposed,
    ce.clicked,
    ce.converted,
    ce.revenue_amount,
--
    -- LEFT JOIN 결과가 NULL이면 해당 정보가 없었다는 뜻이므로 0으로 보정합니다.
    COALESCE(acct.account_count, 0) AS `account_count`,
    COALESCE(acct.active_balance, 0) AS `active_balance`,
    COALESCE(loan.loan_count, 0) AS `loan_count`,
    COALESCE(loan.active_loan_principal, 0) AS `active_loan_principal`,
    COALESCE(loan.max_overdue_days, 0) AS `max_overdue_days`,
    COALESCE(txn.txn_90d, 0) AS `txn_90d`,
    COALESCE(txn.inflow_90d, 0) AS `inflow_90d`,
    COALESCE(txn.outflow_90d, 0) AS `outflow_90d`,
    COALESCE(consent.ai_profiling_granted, 0) AS `ai_profiling_granted`
FROM ce
LEFT JOIN acct
  ON acct.experiment_id = ce.experiment_id
LEFT JOIN loan
  ON loan.experiment_id = ce.experiment_id
LEFT JOIN txn
  ON txn.experiment_id = ce.experiment_id
LEFT JOIN consent
  ON consent.experiment_id = ce.experiment_id
ORDER BY ce.assigned_at;  -- 배정시점 순서로 최종 결과를 확인합니다.

13. CTE 결과를 검증하는 방법

쿼리가 실행된다는 것과 데이터가 올바르다는 것은 다릅니다. 특히 집계와 JOIN이 포함된 CTE는 Grain과 행 수를 반드시 확인합니다.

이 주제에서 확인할 것
무엇을 만들려는가?

CTE가 실행됐다는 사실만으로 끝내지 않고, 중간 결과와 최종 Grain이 실제로 올바른지 검증합니다.

왜 필요한가?

SQL 문법 오류보다 더 위험한 것은 조용히 잘못된 데이터가 만들어지는 경우입니다. 키 중복, Fan-out, 미래정보 포함 여부를 숫자로 확인해야 합니다.

어떤 데이터를 사용하는가?

각 CTE의 결과와 최종 결과

실행하면 무엇이 보여야 하는가?

전체 행 수와 고유 키 수가 기대대로 맞고, 최종 키가 중복되지 않으며, 기준시점 이후 데이터가 섞이지 않았음을 확인합니다.

최종 Grain

검증 대상에 따라 customer_id 또는 experiment_id Grain 유지 여부 확인

각 CTE의 한 행이 무엇인지 말할 수 있는가?
GROUP BY 전후 Grain 변화가 예상과 같은가?
최종 키가 중복되지 않는가?
JOIN 후 행 수가 예상보다 증가하지 않았는가?
기준시점 이후의 미래 데이터가 섞이지 않았는가?
NULL을 0으로 바꿔도 의미상 맞는 컬럼인가?

13-1. 고객 요약 CTE의 유일성 확인

WITH approved AS (
    SELECT
        payment_id,
        customer_id,
        amount
    FROM card_payments
    WHERE is_approved = 1
),
customer_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS payment_count,
        SUM(amount) AS total_amount
    FROM approved
    GROUP BY customer_id
)
SELECT
    COUNT(*) AS customer_rows,
    COUNT(DISTINCT customer_id) AS distinct_customers,
    SUM(payment_count) AS summed_payment_count
FROM customer_summary;
검증 해석
customer_rows와 distinct_customers가 같다면 고객 1명 = 1행 Grain이 유지되고 있다는 뜻입니다.
디버깅 방법
긴 CTE에 문제가 있으면 마지막 SELECT만 보지 말고, 각 CTE 정의 안의 SELECT를 독립 쿼리로 복사해 행 수·키 중복·NULL을 차례로 확인합니다.

14. 확인 문제

문제 1 — 서브쿼리와 CTE의 가장 큰 구조적 차이는 무엇인가?

답: 서브쿼리는 다른 SQL 내부에 중첩되는 반면, CTE는 WITH 절에서 중간 결과를 이름 붙여 위에서 아래로 단계화합니다.

문제 2 — CTE를 사용하면 항상 더 빠른가?

답: 아닙니다. 성능은 DBMS와 실행계획에 따라 달라집니다. CTE의 대표 장점은 가독성·단계 분리·재사용·Grain 관리·검증 편의성입니다.

문제 3 — GROUP BY customer_id 전후의 Grain은 어떻게 달라지는가?

답: 결제 원천에서는 payment_id 1건이 한 행이지만, 고객별 집계 후에는 customer_id 1명이 한 행이 됩니다.

문제 4 — accounts와 transactions를 customers에 그대로 동시에 JOIN할 때 Fan-out이 발생하는 이유는?

답: 두 테이블 모두 고객 기준 1:N이므로 계좌와 거래의 가능한 조합이 생성되어 고객 행이 여러 번 복제될 수 있기 때문입니다.

문제 5 — assigned_at 이후의 거래를 Snapshot에 포함하면 왜 문제가 되는가?

답: 배정 당시 알 수 없던 미래 정보가 들어가므로 Point-in-Time 원칙을 위반하고 Data Leakage가 발생할 수 있습니다.

문제 6 — 긴 CTE를 읽을 때 가장 먼저 확인할 것은?

답: 기준 CTE와 최종 Grain을 먼저 찾고, 각 CTE의 입력 → 처리 → 출력 Grain을 순서대로 확인합니다.
