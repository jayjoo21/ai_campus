1. Window Function은 왜 필요한가?

금융 데이터에서는 개별 거래 1건을 그대로 보고 싶으면서 동시에 그 거래가 속한 고객의 합계·평균·순위·직전값도 함께 보고 싶은 경우가 많습니다. 이때 Window Function이 필요합니다.

이 쿼리를 작성하는 목적
무엇을 만들려는가?

결제 1건을 그대로 유지하면서 같은 고객의 전체 결제금액을 각 결제행 옆에 붙입니다.

왜 필요한가?

GROUP BY를 사용하면 고객별 합계는 구할 수 있지만 payment_id·결제시각·개별 금액이 사라집니다. FDS처럼 개별 이벤트를 유지해야 하는 분석에서는 상세 행을 보존해야 합니다.

어떤 데이터를 사용하는가?

fintech_fraud_lab_class.card_payments

실행하면 무엇이 보여야 하는가?

각 결제행에 amount와 같은 고객의 total_customer_spent가 함께 보입니다.

최종 Grain

payment_id 1건 = 1행

GROUP BY

이 쿼리에서 원하는 결과: 고객별 총 결제금액만 보고 싶습니다. 상세 결제는 필요하지 않은 요약 결과입니다.
USE fintech_fraud_lab_class;
-- [목적] 고객별 총 결제금액만 요약합니다.
SELECT
    customer_id,
    SUM(amount) AS `total_customer_spent`
FROM card_payments
GROUP BY customer_id;

결과: 고객 1명 = 1행. 개별 결제행은 사라집니다.

Window Function

이 쿼리에서 원하는 결과: 결제 1건의 상세 정보는 그대로 두고, 같은 고객의 총 결제금액을 각 결제행 옆에 함께 보고 싶습니다.
USE fintech_fraud_lab_class;
-- [목적] 개별 결제를 그대로 보면서
-- 같은 고객의 전체 결제금액을 각 결제행 옆에 붙입니다.
SELECT
    payment_id,                       -- 개별 결제 PK
    customer_id,                      -- 고객 ID
    amount,                           -- 이 결제의 금액
    SUM(amount) OVER (
        PARTITION BY customer_id      -- 고객별로 합계를 따로 계산
    ) AS `total_customer_spent`
FROM card_payments
ORDER BY customer_id, payment_id
LIMIT 200;

결과: 결제 1건 = 1행을 유지하면서 고객별 합계가 옆에 붙습니다.

GROUP BY와 Window Function의 차이
결제 6행고객 A 3건 + 고객 B 3건
→
GROUP BY고객별 요약
→
고객 2행상세 결제는 사라짐
결제 6행원본 상세
→
Window계산값 추가
→
결제 6행상세 유지 + 집계값

1-1. 같은 행에서 개별 금액과 고객 전체 금액 비교

이 쿼리를 작성하는 목적
무엇을 만들려는가?

각 결제가 고객 전체 결제금액에서 차지하는 비율을 계산합니다.

왜 필요한가?

행 수준 값과 그룹 수준 집계값을 한 행에서 비교하면 ‘평소보다 큰 결제’ 같은 이상패턴을 탐색하기 쉬워집니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

amount, total_customer_spent, spent_ratio_pct가 같은 행에 함께 표시됩니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 개별 결제금액과 고객 전체 결제금액을 같은 행에서 비교합니다.
SELECT
    payment_id,
    customer_id,
    amount,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS `total_customer_spent`,
    ROUND(
        amount
        / NULLIF(
            SUM(amount) OVER (PARTITION BY customer_id),
            0
        )
        * 100,
        2
    ) AS `spent_ratio_pct`
FROM card_payments
ORDER BY customer_id, payment_id
LIMIT 200;
NULLIF(...,0)는 왜 쓰나?
분모가 0이면 0으로 나누는 오류가 발생할 수 있으므로, 분모가 0일 때 NULL로 바꾸어 계산 오류를 방지합니다.

1-2. CTE + JOIN으로도 가능하지만 Window가 더 직접적이다

두 방법을 비교하는 목적
무엇을 만들려는가?

같은 ‘개별 결제 + 고객별 총액’ 결과를 CTE+JOIN과 Window Function 두 방식으로 만들어 구조 차이를 확인합니다.

왜 필요한가?

Window Function이 왜 등장했는지 이해하려면 기존 방식으로도 같은 결과를 만들 수 있다는 점을 먼저 알아야 합니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

두 방식 모두 결제 1건을 유지하면서 고객별 총액이 붙지만, Window 방식은 집계 CTE를 다시 JOIN하는 구조가 필요하지 않습니다.

최종 Grain

payment_id 1건 = 1행

CTE + JOIN

이 쿼리에서 원하는 결과: CTE에서 고객별 총액을 먼저 만든 뒤 원본 결제에 다시 JOIN하여 ‘개별 결제 + 고객 총액’을 함께 봅니다.
USE fintech_fraud_lab_class;
-- =========================================================
-- [Window Function을 사용하지 않는 방법]
-- 앞 시간에 배운 CTE를 이용해 고객별 총 결제금액을 먼저 계산한 뒤
-- 원본 결제 테이블에 다시 JOIN합니다.
-- =========================================================
-- ① customer_total CTE: 고객별 총 결제금액을 1행으로 집계합니다.
WITH customer_total AS (
    SELECT
        customer_id,                    -- 고객별로 그룹화할 기준 컬럼
        SUM(amount) AS `total_spent`    -- 해당 고객의 모든 결제금액 합계
    FROM card_payments
    GROUP BY customer_id                -- 고객 1명 = 1행으로 집계
)
-- ② 원본 결제행에 CTE의 고객별 집계값을 다시 붙입니다.
SELECT
    cp.payment_id,                      -- 개별 결제 ID
    cp.customer_id,                     -- 고객 ID
    cp.amount,                          -- 개별 결제금액
    ct.total_spent                      -- CTE에서 계산한 고객 총 결제금액
FROM card_payments AS cp
INNER JOIN customer_total AS ct
  ON cp.customer_id = ct.customer_id    -- 같은 고객의 집계값을 원본 행에 연결
ORDER BY cp.customer_id, cp.payment_id
LIMIT 200;

Window Function

이 쿼리에서 원하는 결과: 별도 재JOIN 없이 Window Function 하나로 같은 ‘개별 결제 + 고객 총액’ 결과를 만듭니다.
USE fintech_fraud_lab_class;
-- =========================================================
-- [Window Function을 사용하는 방법]
-- 별도의 집계 CTE와 재JOIN 없이
-- 원본 결제행을 유지하면서 고객별 총액을 바로 붙입니다.
-- =========================================================
SELECT
    payment_id,                         -- 개별 결제 ID
    customer_id,                        -- 고객 ID
    amount,                             -- 개별 결제금액
    SUM(amount) OVER (
        PARTITION BY customer_id        -- 고객별 합계를 계산하지만 행은 줄이지 않음
    ) AS `total_spent`
FROM card_payments
ORDER BY customer_id, payment_id
LIMIT 200;
성능에 대한 주의
Window Function이 항상 더 빠르다고 단정할 수는 없습니다. 실제 성능은 인덱스·정렬·데이터량·실행계획에 따라 달라집니다. 여기서의 핵심은 상세 행을 유지하면서 그룹 계산을 표현하기 더 자연스럽다는 점입니다.

2. Window Function에서 자주 만나는 핵심 용어

Window Function윈도우 함수

행을 줄이지 않고 다른 행과의 관계를 이용해 계산값을 붙이는 함수입니다.

OVER()계산창 정의

Window Function이 어떤 그룹과 순서를 기준으로 계산할지 지정하는 괄호입니다.

PARTITION BY그룹 나누기

전체 행을 고객별·종목별처럼 독립된 계산 그룹으로 나눕니다. GROUP BY와 달리 행을 줄이지 않습니다.

ORDER BY그룹 안 순서

각 그룹 안에서 시간순·금액순 등 계산 순서를 정합니다.

Window Frame계산 범위

현재 행을 기준으로 실제 계산에 포함할 앞·뒤 행의 범위를 지정합니다.

ROW_NUMBER()고유 순번

정렬순서대로 1,2,3… 번호를 붙입니다. 동점이어도 서로 다른 번호를 줍니다.

RANK()공동 순위

동점은 같은 순위이며 다음 순위를 건너뜁니다.

DENSE_RANK()연속 공동 순위

동점은 같은 순위지만 다음 순위를 건너뛰지 않습니다.

LAG()이전 행 값

현재 행에서 이전 행의 값을 가져옵니다.

Point-in-Time시점 정합성

판단 시점 이후의 미래 정보를 사용하지 않는 원칙입니다.

As-of기준시점 최신값

특정 시점 이전에 존재하는 값 중 가장 최근 값을 연결하는 방식입니다.

Grain한 행의 단위

결과 한 행이 무엇을 의미하는지 나타냅니다. Window Function은 보통 원본 Grain을 유지합니다.

4. ROW_NUMBER — 그룹 안에서 순번 붙이기

이 쿼리를 작성하는 목적
무엇을 만들려는가?

고객 1002의 결제를 시간순으로 정렬하고 각 결제에 1, 2, 3… 순번을 붙입니다.

왜 필요한가?

Window Function이 원본 행을 없애지 않고 계산 컬럼을 추가한다는 가장 기본적인 동작을 확인하기 좋습니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

고객 1002의 결제가 시간순으로 나오고 payment_seq가 1부터 증가합니다.

최종 Grain

payment_id 1건 = 1행

-- 사용할 금융 실습 DB를 명시합니다.
USE fintech_fraud_lab_class;
-- [목적] 고객 1002의 결제를 시간순으로 나열하고 1, 2, 3... 순번을 붙입니다.
SELECT
    payment_id,                 -- 결제 1건의 PK
    customer_id,                -- 어떤 고객의 결제인지
    payment_at,                 -- 결제시각
    amount,                     -- 결제금액
    ROW_NUMBER() OVER (         -- 각 행에 1부터 시작하는 고유 순번을 부여
        ORDER BY payment_at,    -- 먼저 결제시각이 빠른 순서
                 payment_id     -- 같은 시각이면 PK로 순서를 확정
    ) AS `payment_seq`
FROM card_payments
WHERE customer_id = 1002        -- 처음에는 한 고객만 보며 원리를 이해
ORDER BY payment_at, payment_id
LIMIT 30;

4-1. PARTITION BY를 추가하면

이 쿼리를 작성하는 목적
무엇을 만들려는가?

모든 고객을 한 번에 조회하면서 고객이 바뀔 때마다 순번을 다시 1부터 시작하게 합니다.

왜 필요한가?

실제 데이터에서는 고객 한 명씩 따로 조회하지 않고 한 SQL에서 고객별 독립 순번을 계산해야 합니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

customer_id가 바뀔 때마다 payment_seq가 다시 1부터 시작합니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 모든 고객을 조회하되 고객이 바뀔 때마다 순번을 다시 1부터 시작합니다.
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id       -- 고객별로 서로 독립된 Window를 생성
        ORDER BY payment_at, payment_id -- 각 고객 안에서 시간순으로 정렬
    ) AS `payment_seq`
FROM card_payments
ORDER BY customer_id, payment_at, payment_id
LIMIT 200;

5. ROW_NUMBER · RANK · DENSE_RANK — 동점 처리 방식 비교

세 함수는 모두 순위를 계산하지만 동점이 있을 때 결과가 달라집니다.

이 쿼리를 작성하는 목적
무엇을 만들려는가?

동점 금액이 확실히 존재하는 작은 데이터에서 세 순위 함수의 차이를 확인합니다.

왜 필요한가?

실제 데이터에서는 같은 금액이 없으면 세 함수가 모두 비슷해 보여 차이를 이해하기 어렵습니다. 먼저 동점을 의도적으로 만든 데이터로 원리를 확인합니다.

어떤 데이터를 사용하는가?

CTE로 만든 5행의 임시 sample_payments

실행하면 무엇이 보여야 하는가?

500000 두 건과 200000 두 건에서 ROW_NUMBER, RANK, DENSE_RANK가 서로 다르게 나타납니다.

최종 Grain

결제 예시 1행 = 1행

USE fintech_fraud_lab_class;
-- =========================================================
-- [목적]
-- ROW_NUMBER, RANK, DENSE_RANK의 차이를
-- 동점이 있는 작은 예제로 확실하게 확인합니다.
-- =========================================================
-- ① sample_payments CTE:
-- 실제 DB를 수정하지 않고 예시 5행 데이터를 임시로 만듭니다.
WITH sample_payments AS (
    SELECT 1 AS payment_id, 1002 AS customer_id, 500000 AS amount
    UNION ALL
    SELECT 2, 1002, 500000
    UNION ALL
    SELECT 3, 1002, 300000
    UNION ALL
    SELECT 4, 1002, 200000
    UNION ALL
    SELECT 5, 1002, 200000
)
-- ② 같은 amount를 기준으로 세 순위 함수를 비교합니다.
SELECT
    payment_id,
    customer_id,
    amount,
    -- ROW_NUMBER:
    -- 동점이어도 각 행에 반드시 서로 다른 번호를 부여합니다.
    ROW_NUMBER() OVER (
        ORDER BY amount DESC
    ) AS `row_number_rank`,
    -- RANK:
    -- 동점은 같은 순위가 되고,
    -- 다음 순위는 동점자 수만큼 건너뜁니다.
    RANK() OVER (
        ORDER BY amount DESC
    ) AS `rank_value`,
    -- DENSE_RANK:
    -- 동점은 같은 순위가 되지만
    -- 다음 순위를 건너뛰지 않습니다.
    DENSE_RANK() OVER (
        ORDER BY amount DESC
    ) AS `dense_rank_value`
FROM sample_payments
ORDER BY amount DESC, payment_id;

5-1. 실제 고객별 고액 결제 순위

이 쿼리를 작성하는 목적
무엇을 만들려는가?

각 고객 안에서 결제금액이 큰 순서대로 세 종류의 순위를 계산합니다.

왜 필요한가?

고액결제를 고객별로 비교하거나 상위 거래를 찾을 때 순위 함수가 필요합니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

고객이 바뀌면 순위가 다시 1부터 시작하고, 같은 금액이 있으면 RANK와 DENSE_RANK에서 공동 순위가 보입니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- =========================================================
-- [목적]
-- 실제 카드결제 데이터에서
-- 고객마다 결제금액이 큰 순서대로 세 종류의 순위를 계산합니다.
-- =========================================================
SELECT
    payment_id,                         -- 결제 PK
    customer_id,                        -- 고객 ID
    payment_at,                         -- 결제 시각
    amount,                             -- 결제 금액
    -- ROW_NUMBER:
    -- 같은 금액이 여러 건이어도 payment_id로 순서를 확정해
    -- 모든 결제에 서로 다른 순번을 줍니다.
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY amount DESC, payment_id
    ) AS `payment_order`,
    -- RANK:
    -- 같은 금액이면 같은 순위,
    -- 다음 순위는 동점자 수만큼 건너뜁니다.
    RANK() OVER (
        PARTITION BY customer_id
        ORDER BY amount DESC
    ) AS `amount_rank`,
    -- DENSE_RANK:
    -- 같은 금액이면 같은 순위,
    -- 다음 순위를 건너뛰지 않습니다.
    DENSE_RANK() OVER (
        PARTITION BY customer_id
        ORDER BY amount DESC
    ) AS `amount_dense_rank`
FROM card_payments
ORDER BY customer_id, amount DESC, payment_id
LIMIT 300;

5-2. 고객별 상위 3건만 남기기

이 쿼리를 작성하는 목적
무엇을 만들려는가?

Window Function으로 계산한 순번을 이용해 고객별 고액 결제 상위 3건만 추립니다.

왜 필요한가?

MySQL에서는 같은 SELECT에서 만든 Window 별칭을 WHERE에서 바로 사용할 수 없으므로 CTE로 한 번 감싸야 합니다.

어떤 데이터를 사용하는가?

card_payments + CTE ranked_payments

실행하면 무엇이 보여야 하는가?

각 고객마다 payment_order 1~3에 해당하는 최대 3개의 결제만 남습니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 고객별 결제금액 상위 3건만 선택합니다.
WITH ranked_payments AS (
    SELECT
        payment_id,
        customer_id,
        payment_at,
        amount,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, payment_id
        ) AS `payment_order`
    FROM card_payments
)
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    `payment_order`
FROM ranked_payments
WHERE `payment_order` <= 3
ORDER BY customer_id, `payment_order`;

6. LAG — 현재 행에서 직전값 가져오기

6-1. 삼성전자 전일 종가

이 쿼리를 작성하는 목적
무엇을 만들려는가?

각 거래일의 현재 종가 옆에 바로 전 거래일 종가를 붙입니다.

왜 필요한가?

시계열 분석에서는 현재값만으로는 변화량을 알 수 없습니다. 직전값이 있어야 전일 대비 상승·하락 같은 변화를 계산할 수 있습니다.

어떤 데이터를 사용하는가?

stock_data.stock_prices

실행하면 무엇이 보여야 하는가?

첫 거래일은 이전 값이 없어 prev_close_price = NULL, 이후 행에는 직전 거래일 종가가 표시됩니다.

최종 Grain

stock_code × trade_date 1행

-- DB가 바뀌므로 실제 주가 DB를 다시 명시합니다.
USE stock_data;
-- [목적] 삼성전자 각 거래일의 현재 종가 옆에 바로 전 거래일 종가를 붙입니다.
SELECT
    stock_code,
    trade_date,
    close_price,
    LAG(close_price) OVER (
        PARTITION BY stock_code    -- 종목이 바뀌면 직전값 계산을 다시 시작
        ORDER BY trade_date        -- 거래일 순서가 곧 시계열 순서
    ) AS `prev_close_price`
FROM stock_prices
WHERE stock_code = '005930'
ORDER BY trade_date
LIMIT 100;

왜 필요한가?

FDS에서는 현재 결제가 직전 결제와 얼마나 가까운 시간에 발생했는지가 이상패턴 판단에 유용할 수 있습니다.

어떤 데이터를 사용하는가?

실행하면 무엇이 보여야 하는가?

최종 Grain

payment_id 1건 = 1행

-- 금융 DB로 다시 바뀌므로 USE를 명시합니다.
USE fintech_fraud_lab_class;

7. 누적값 — 현재 행까지 계속 더하기

이 쿼리를 작성하는 목적
무엇을 만들려는가?

고객별 결제를 시간순으로 보면서 현재 결제까지의 누적 결제금액을 계산합니다.

왜 필요한가?

누적합은 시간이 흐르면서 고객의 지출 규모가 어떻게 쌓이는지 확인할 때 사용합니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

첫 결제는 누적합이 자신의 금액과 같고, 이후 행으로 갈수록 이전 누적합에 현재 금액이 더해집니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 고객별 결제 흐름을 시간순으로 보면서
-- 현재 결제까지의 누적 결제금액을 계산합니다.
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    SUM(amount) OVER (
        PARTITION BY customer_id
        ORDER BY payment_at, payment_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS `running_total_amount`
FROM card_payments
ORDER BY customer_id, payment_at, payment_id
LIMIT 300;
UNBOUNDED PRECEDING
현재 Partition의 맨 처음 행부터 시작한다는 뜻입니다. CURRENT ROW는 현재 행까지 포함한다는 뜻입니다.

8. Window Frame — 현재 행 이전의 일정 범위만 계산하기

FDS에서 현재 결제가 평소보다 큰지를 보려면 현재 결제 자신을 평균에 포함하면 안 됩니다. 따라서 Frame을 이용해 현재 이전의 과거 행만 계산합니다.

ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
과거 5
과거 4
과거 3
과거 2
과거 1
현재
미래
초록색 3개 행만 평균에 포함되고 현재 행은 제외됩니다.

8-1. 직전 3건 평균

이 쿼리를 작성하는 목적
무엇을 만들려는가?

현재 결제를 제외하고 바로 이전 최대 3건의 평균 결제금액을 계산합니다.

왜 필요한가?

현재 이벤트가 과거 기준선 계산에 들어가면 기준선이 현재값의 영향을 받아 이상도를 왜곡할 수 있습니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

첫 결제는 NULL, 두 번째는 이전 1건 평균, 세 번째는 이전 2건 평균, 네 번째부터 최대 이전 3건 평균이 표시됩니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 고객별 현재 결제 직전 3건의 평균 결제금액을 확인합니다.
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    AVG(amount) OVER (
        PARTITION BY customer_id
        ORDER BY payment_at, payment_id
        ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
        -- 3 PRECEDING: 현재행보다 3행 앞에서 시작
        -- 1 PRECEDING: 현재행 바로 직전에서 종료
        -- 따라서 현재 결제금액은 평균 계산에 포함되지 않음
    ) AS `prior_3_avg_amount`
FROM card_payments
ORDER BY customer_id, payment_at, payment_id
LIMIT 300;

8-2. 직전 10건 평균

이 쿼리를 작성하는 목적
무엇을 만들려는가?

같은 원리를 직전 최대 10건까지 확장해 더 넓은 과거 기준선을 만듭니다.

왜 필요한가?

짧은 과거와 긴 과거는 서로 다른 행동 기준선을 만들 수 있으므로 관찰 범위를 조절하는 개념을 이해할 수 있습니다.

어떤 데이터를 사용하는가?

card_payments

실행하면 무엇이 보여야 하는가?

각 결제행에 현재 이전 최대 10건의 평균이 prior_10_avg_amount로 표시됩니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
-- [목적] 원리는 같고 관찰 범위만 직전 10건으로 넓힙니다.
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    AVG(amount) OVER (
        PARTITION BY customer_id

9. CTE + ROW_NUMBER — 그룹별 최신 1건 선택

이 쿼리를 작성하는 목적
무엇을 만들려는가?

고객별 신용보고서를 최신순으로 정렬한 뒤 가장 최신 보고서 1건만 남깁니다.

왜 필요한가?

한 고객에게 신용보고서가 여러 건 존재하면 현재 상태를 대표할 한 건을 선택해야 할 때가 있습니다.

어떤 데이터를 사용하는가?

bureau_reports

실행하면 무엇이 보여야 하는가?

보고서가 있는 고객은 고객당 최대 1행만 반환되고, 가장 최신 report_date가 선택됩니다.

최종 Grain

customer_id 1명 = 최대 1행

USE fintech_fraud_lab_class;
-- [1단계] 고객별 report를 최신순으로 정렬하고 순번을 붙입니다.
WITH ranked AS (
    SELECT
        br.report_id,
        br.customer_id,
        br.report_date,
        br.external_credit_score,
        ROW_NUMBER() OVER (
            PARTITION BY br.customer_id
            ORDER BY br.report_date DESC, br.report_id DESC
            -- 최신 날짜가 1순위
            -- 같은 날짜가 여러 건이면 report_id가 큰 행을 우선
        ) AS `rn`
    FROM bureau_reports AS br
)
-- [2단계] 각 고객의 순번 1번만 남겨 현재 기준 최신 report를 선택합니다.
SELECT
    report_id,
    customer_id,
    report_date,
    external_credit_score
FROM ranked
WHERE `rn` = 1
ORDER BY customer_id;
이 쿼리만으로는 과거 대출심사 데이터에 사용할 수 없습니다.
‘현재 기준 최신 보고서’는 과거 신청 당시에는 존재하지 않았을 수 있습니다. 과거 시점의 판단에는 신청시점 이전 최신값이 필요합니다.

10. Point-in-Time / As-of — 신청시점 이전 최신 보고서 찾기

대출 신청을 평가할 때는 오늘 가장 최신 보고서가 아니라 그 신청이 발생했던 당시 사용할 수 있었던 가장 최신 신용보고서를 연결해야 합니다.

이 쿼리를 작성하는 목적
무엇을 만들려는가?

각 대출 신청마다 신청일 이후의 미래 보고서를 제외하고, 신청시점 이전에 존재하던 보고서 중 가장 최신 1건을 연결합니다.

왜 필요한가?

미래 정보를 섞으면 모델이 실제 운영 당시 알 수 없었던 정보를 학습하게 되어 성능이 과대평가되는 Data Leakage가 발생합니다.

어떤 데이터를 사용하는가?

loan_applications, bureau_reports

실행하면 무엇이 보여야 하는가?

각 application_id마다 최대 1행이 나오고, 선택된 report_date는 반드시 신청일보다 같거나 이전이어야 합니다.

최종 Grain

application_id 1건 = 1행

As-of 선택 원리
2025-01-10report A
후보
2025-04-02report B
가장 최신 후보
2025-05-15대출 신청
기준시점
2025-06-20report C
미래 정보 → 제외
USE fintech_fraud_lab_class;
-- [최종형] 대출 신청마다 "신청 당시 알 수 있었던 최신 bureau report" 1건을 찾습니다.
-- 최종 Grain: application_id 1건 = 1행
-- ① candidates CTE: 신청별로 사용할 수 있는 과거 report 후보를 만들고 최신순 순번을 붙입니다.
WITH candidates AS (
    SELECT
        la.application_id,                -- 대출 신청의 PK
        la.customer_id,                   -- 신청 고객
        la.application_at,                -- Point-in-Time 기준시점
        br.report_id,                     -- 외부 신용보고서 ID
        br.report_date,                   -- 보고서 기준일
        br.external_credit_score,         -- 신청 당시 사용할 외부 신용점수 후보
        ROW_NUMBER() OVER (
            PARTITION BY la.application_id -- 대출 신청마다 순번을 새로 시작
            ORDER BY
                br.report_date DESC,       -- 신청일 이전 중 가장 최근 report를 우선
                br.report_id DESC          -- 같은 날짜면 큰 report_id를 우선해 한 건으로 확정
        ) AS `rn`
    FROM loan_applications AS la
    LEFT JOIN bureau_reports AS br
      ON la.customer_id = br.customer_id
     AND br.report_date <= DATE(la.application_at)
     -- 가장 중요한 시점 조건:
     -- 신청 이후 생성된 report는 미래정보이므로 후보 단계에서 제거
)
-- ② 바깥 SELECT: 신청별 가장 최신 후보 한 건만 선택합니다.
SELECT
    application_id,
    customer_id,
    application_at,
    report_id,
    report_date,
    external_credit_score
FROM candidates
WHERE `rn` = 1
ORDER BY application_at, application_id;
핵심 순서
고객 연결 → report_date ≤ application_at로 미래 제외 → 신청별 최신순 정렬 → ROW_NUMBER() → rn=1.

11. 시점 데이터는 반드시 검증하기

쿼리가 오류 없이 실행되어도 잘못된 미래 정보가 조용히 섞일 수 있습니다. 시점 데이터는 결과 자체를 검증하는 SQL을 별도로 작성하는 것이 안전합니다.

11-1. 미래 보고서가 섞였는지 확인

검증 쿼리의 목적
무엇을 만들려는가?

최종 선택된 보고서 중 신청일 이후의 미래 보고서가 한 건이라도 있는지 셉니다.

왜 필요한가?

Point-in-Time 쿼리에서 가장 위험한 오류는 미래정보 누수이므로 숫자로 0건인지 확인해야 합니다.

어떤 데이터를 사용하는가?

loan_applications, bureau_reports

실행하면 무엇이 보여야 하는가?

leakage_rows = 0이어야 합니다.

최종 Grain

검증 결과 1행

USE fintech_fraud_lab_class;
-- [검증 목적] 최종 선택된 bureau report 중 신청일 이후 report가 한 건이라도 있는지 확인합니다.
WITH candidates AS (
    SELECT
        la.application_id,
        la.application_at,
        br.report_date,
        ROW_NUMBER() OVER (
            PARTITION BY la.application_id
            ORDER BY br.report_date DESC, br.report_id DESC
        ) AS `rn`
    FROM loan_applications AS la
    LEFT JOIN bureau_reports AS br
      ON la.customer_id = br.customer_id
     AND br.report_date <= DATE(la.application_at)
)
SELECT
    COUNT(*) AS `leakage_rows`
FROM candidates
WHERE `rn` = 1
  AND report_date > DATE(application_at);

11-2. 신청 1건 = 1행인지 확인

검증 쿼리의 목적
무엇을 만들려는가?

최종 선택 결과에서 같은 application_id가 여러 번 나오는지 확인합니다.

왜 필요한가?

최종 모델 입력의 Grain이 신청 1건이라면 신청 ID가 중복되어서는 안 됩니다.

어떤 데이터를 사용하는가?

선택된 As-of 결과

실행하면 무엇이 보여야 하는가?

selected_rows와 distinct_applications가 같아야 합니다.

최종 Grain

검증 결과 1행

USE fintech_fraud_lab_class;
-- [검증 목적] 선택 결과에서 application_id 중복이 있는지 확인합니다.
WITH candidates AS (
    SELECT
        la.application_id,
        ROW_NUMBER() OVER (
            PARTITION BY la.application_id
            ORDER BY br.report_date DESC, br.report_id DESC
        ) AS `rn`
    FROM loan_applications AS la
    LEFT JOIN bureau_reports AS br
      ON la.customer_id = br.customer_id
     AND br.report_date <= DATE(la.application_at)
),
selected AS (
    SELECT application_id
    FROM candidates
    WHERE `rn` = 1
)
SELECT
    COUNT(*) AS `selected_rows`,
    COUNT(DISTINCT application_id) AS `distinct_applications`
FROM selected;
선택된 report_date가 application_at 이후가 아닌가?
application_id가 중복되지 않는가?
과거 보고서가 없는 신청은 NULL로 남는가?
동일 날짜 보고서가 있을 때 tie-break 기준이 있는가?

13. 실습 쿼리 — 목적과 기대 결과를 먼저 확인하고 실행하기

각 SQL을 실행하기 전에 원하는 결과를 먼저 확인합니다. 코드를 외우는 것이 아니라, 필요한 결과를 만들기 위해 PARTITION·ORDER·Frame·시점조건을 선택하는 흐름을 익히는 것이 핵심입니다.

13-1. 고객별 결제 순번을 붙이세요.

이 실습 쿼리를 작성하는 목적
무엇을 만들려는가?

각 고객의 결제를 시간순으로 나열하고 고객별로 1, 2, 3… 순번을 붙입니다.

왜 필요한가?

PARTITION BY와 ORDER BY가 어떻게 함께 작동하는지 가장 직접적으로 확인할 수 있습니다.

어떤 데이터를 사용하는가?

fintech_fraud_lab_class.card_payments

실행하면 무엇이 보여야 하는가?

고객이 바뀔 때마다 payment_seq가 다시 1부터 시작합니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY payment_at, payment_id
    ) AS `payment_seq`
FROM card_payments
ORDER BY customer_id, payment_at, payment_id;

13-2. 삼성전자 전일 종가를 붙이세요.

이 실습 쿼리를 작성하는 목적
무엇을 만들려는가?

삼성전자 각 거래일의 종가 옆에 바로 전 거래일 종가를 붙입니다.

왜 필요한가?

직전값을 가져오는 LAG의 동작을 실제 시계열 데이터에서 확인하고 pandas shift(1)과 연결할 수 있습니다.

어떤 데이터를 사용하는가?

stock_data.stock_prices

실행하면 무엇이 보여야 하는가?

첫 거래일은 이전 종가가 없어 NULL이고 이후 행에는 전 거래일 종가가 표시됩니다.

최종 Grain

stock_code × trade_date 1행

USE stock_data;
SELECT
    stock_code,
    trade_date,
    close_price,
    LAG(close_price) OVER (
        PARTITION BY stock_code
        ORDER BY trade_date
    ) AS `prev_close_price`
FROM stock_prices
WHERE stock_code = '005930'
ORDER BY trade_date;

13-3. 고객별 직전 5건 평균 결제금액을 구하세요.

이 실습 쿼리를 작성하는 목적
무엇을 만들려는가?

각 결제에 대해 현재 결제를 제외한 직전 최대 5건의 평균 결제금액을 계산합니다.

왜 필요한가?

현재값을 과거 기준선에 포함하지 않는 Window Frame의 원리를 확인합니다.

어떤 데이터를 사용하는가?

fintech_fraud_lab_class.card_payments

실행하면 무엇이 보여야 하는가?

첫 결제는 NULL이며 이후 행에는 가능한 과거 최대 5건 평균이 표시됩니다.

최종 Grain

payment_id 1건 = 1행

USE fintech_fraud_lab_class;
SELECT
    payment_id,
    customer_id,
    payment_at,
    amount,
    AVG(amount) OVER (
        PARTITION BY customer_id
        ORDER BY payment_at, payment_id
        ROWS BETWEEN 5 PRECEDING AND 1 PRECEDING
    ) AS `prior_5_avg_amount`
FROM card_payments
ORDER BY customer_id, payment_at, payment_id;

13-4. 신청시점 이전 최신 bureau report를 선택하세요.

이 실습 쿼리를 작성하는 목적
무엇을 만들려는가?

각 대출 신청마다 신청시점 이전에 존재했던 신용보고서 중 가장 최신 1건을 선택합니다.

왜 필요한가?

Point-in-Time과 As-of 원리를 적용해 미래 신용정보가 모델 입력에 섞이지 않도록 하기 위해 필요합니다.

어떤 데이터를 사용하는가?

loan_applications, bureau_reports

실행하면 무엇이 보여야 하는가?

각 application_id가 최대 1행이며 선택된 report_date는 application_at보다 이후가 아니어야 합니다.

최종 Grain

application_id 1건 = 1행

USE fintech_fraud_lab_class;
WITH candidates AS (
    SELECT
        la.application_id,
        la.customer_id,
        la.application_at,
        br.report_id,
        br.report_date,
        ROW_NUMBER() OVER (
            PARTITION BY la.application_id
            ORDER BY br.report_date DESC, br.report_id DESC
        ) AS `rn`
    FROM loan_applications AS la
    LEFT JOIN bureau_reports AS br
      ON la.customer_id = br.customer_id
     AND br.report_date <= DATE(la.application_at)
)
SELECT
    application_id,
    customer_id,
    application_at,
    report_id,
    report_date
FROM candidates
WHERE `rn` = 1
ORDER BY application_at, application_id;

14. 확인 문제

문제 1 — 고객별 결제 순번을 붙이려면 PARTITION BY와 ORDER BY에 무엇을 넣어야 하는가?

답: PARTITION BY customer_id, ORDER BY payment_at, payment_id처럼 작성합니다.

문제 2 — ROW_NUMBER와 RANK의 가장 큰 차이는?

답: ROW_NUMBER는 동점이어도 서로 다른 번호를 주고, RANK는 동점에 같은 순위를 부여합니다.

문제 3 — LAG(close_price)는 무엇을 반환하는가?

답: 지정한 정렬순서에서 현재 행의 바로 이전 행에 있는 close_price를 반환합니다.

문제 4 — ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING이 현재 행을 제외하는 이유는?

답: 종료 지점이 CURRENT ROW가 아니라 1 PRECEDING이므로 현재 행 직전에서 계산범위가 끝납니다.

문제 5 — 대출 신청시점 이후의 bureau report를 사용하면 왜 안 되는가?

답: 신청 당시에는 알 수 없던 미래 정보이므로 Data Leakage가 발생합니다.

문제 6 — As-of 결과에서 가장 먼저 확인할 두 가지는?

답: 미래 report가 0건인지, 그리고 application_id가 최종 결과에서 중복되지 않는지 확인합니다.
