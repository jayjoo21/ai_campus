4. ERD를 실제 Database로 만들기 — Forward Engineering

Forward Engineering은 Workbench 모델에 그려진 Schema·Table·PK·FK·Index를 실제 MySQL Server에 생성하는 기능입니다. 테이블을 하나씩 손으로 CREATE할 필요가 없습니다.

Forward Engineering에서 화면이 진행되는 순서
1Connection어느 MySQL Server에 만들지 선택
2Options생성 SQL 옵션 확인
3Select ObjectsSchema/Table 등 생성 대상 선택
4Review SQLCREATE DATABASE/TABLE SQL 확인
5Execute실제 서버에 DDL 실행

Step 1. 모델 탭에서 Forward Engineer 실행

Database→Forward Engineer...

반드시 .mwb 모델 탭이 열린 상태에서 실행합니다. SQL Editor 탭에서 찾으면 원하는 메뉴 흐름과 다르게 느껴질 수 있습니다.

Step 2. Connection Options

앞에서 테스트한 Local MySQL 연결을 선택하고 Next를 누릅니다.

Step 3. Options 화면

초보자 실습에서는 특별한 이유가 없다면 기본값을 유지합니다.

Generate DROP Statements

기존 객체 삭제문을 만들 수 있는 옵션입니다. 새 DB 생성 실습에서는 불필요하며 기존 데이터가 있을 때 위험할 수 있습니다.

Generate INSERT / 기타 옵션

이번 단계의 목적은 구조 생성이므로 CREATE TABLE과 FK가 정상 생성되는지가 핵심입니다.

Step 4. Select Objects

테이블·View·Routine·Trigger 등 Forward Engineering 대상 객체를 선택합니다.

이번 모델에서 확인할 핵심

Step 5. Review SQL Script

Workbench가 ERD를 바탕으로 자동 생성한 DDL을 보여줍니다. 아래 문자열이 있는지 검색해 보세요.

CREATE SCHEMA IF NOT EXISTS `fintech_fraud_lab_class` CREATE SCHEMA IF NOT EXISTS `stock_data` CREATE TABLE ... `customers` CREATE TABLE ... `transactions` CREATE TABLE ... `stocks` CREATE TABLE ... `stock_prices`

DDL을 읽어보는 습관이 중요합니다. 이 단계에서 “내가 예상한 DB와 테이블을 만드는 SQL이 맞는가?”를 확인합니다.

Step 6. Execute / Next

SQL이 맞다면 Next로 진행하여 서버에 실제로 실행합니다. Progress 화면에서 각 작업이 성공했는지 확인하고 Finish합니다.

5. 대량 데이터 적재 직전, InnoDB Buffer Pool을 16GB로 임시 확대

Buffer Pool은 InnoDB가 테이블·인덱스 페이지를 메모리에 캐시하는 공간입니다. 이번 실습에서는 데이터 적재 전에 일시적으로 16GB로 늘리고, 적재와 검증이 끝나면 4GB로 다시 줄입니다.

16GB를 설정하기 전에 PC 메모리를 확인하세요.
이 설정은 MySQL 프로세스가 사용할 수 있는 메모리 규모를 크게 늘립니다. Windows와 Workbench, 브라우저, Python 등이 사용할 여유 RAM이 남아 있어야 합니다. 물리 메모리가 충분하지 않은 PC에서는 16GB로 올리지 말고 더 낮은 값을 사용해야 합니다.

5-1. 현재 값 확인

SELECT VERSION() AS mysql_version, ROUND(@@GLOBAL.innodb_buffer_pool_size / 1024 / 1024 / 1024, 2) AS buffer_pool_gb, ROUND(@@GLOBAL.innodb_buffer_pool_chunk_size / 1024 / 1024, 0) AS chunk_mb;

5-2. 16GB로 변경

-- 16 GiB = 17,179,869,184 bytes SET GLOBAL innodb_buffer_pool_size = 17179869184;
SET GLOBAL을 사용하는 이유
이번 실습에서는 재시작 후에도 유지되는 영구 설정이 아니라 현재 실행 중인 MySQL Server에만 임시 적용합니다. 따라서 my.ini나 SET PERSIST를 수정하지 않습니다.

5-3. resize 완료 확인

SELECT ROUND(@@GLOBAL.innodb_buffer_pool_size / 1024 / 1024 / 1024, 2) AS buffer_pool_gb; SELECT variable_name, variable_value FROM performance_schema.global_status WHERE LOWER(variable_name) LIKE 'innodb_buffer_pool_resize%';
일반 실습 상태4GB평상시 Buffer Pool
대량 적재 직전16GB임시 확대
적재 완료 후4GB반드시 복구
표시값이 정확히 16.00이 아닐 수도 있습니다.
MySQL은 Buffer Pool을 내부 chunk 단위에 맞춰 조정할 수 있습니다. 변경 후 실제 값을 다시 조회하는 것이 중요합니다.

7. Import가 끝났다고 바로 종료하지 말고 데이터 검증

“Import Completed”는 SQL 실행이 끝났다는 뜻입니다. 실제 행이 들어왔는지, 기간이 정상인지, 종목 마스터와 가격 데이터가 연결되는지를 확인해야 적재가 완료된 것입니다.

7-1. 테이블별 행 수

SELECT 'stocks' AS table_name, COUNT(*) AS row_count FROM stock_data.stocks UNION ALL SELECT 'stock_prices', COUNT(*) FROM stock_data.stock_prices UNION ALL SELECT 'stock_collection_log', COUNT(*) FROM stock_data.stock_collection_log;

7-2. 주가 데이터 기간과 종목 수

SELECT COUNT(*) AS price_rows, COUNT(DISTINCT stock_code) AS stock_count, MIN(trade_date) AS first_trade_date, MAX(trade_date) AS last_trade_date FROM stock_data.stock_prices;

7-3. 실제 데이터 20건 보기

SELECT p.stock_code, s.company_name, p.trade_date, p.open_price, p.high_price, p.low_price, p.close_price, p.volume, p.change_rate FROM stock_data.stock_prices AS p JOIN stock_data.stocks AS s ON s.stock_code = p.stock_code ORDER BY p.trade_date DESC, p.stock_code LIMIT 20;

7-4. 종목 마스터에 없는 가격 데이터가 있는지

SELECT COUNT(*) AS orphan_price_rows FROM stock_data.stock_prices AS p LEFT JOIN stock_data.stocks AS s ON s.stock_code = p.stock_code WHERE s.stock_code IS NULL;
정상 기대
orphan_price_rows = 0이면 가격 데이터의 종목코드가 모두 종목 마스터와 연결된 것입니다.

7-5. 학습에 바로 쓸 수 있는 간단한 조회

SELECT s.company_name, p.trade_date, p.close_price, p.volume FROM stock_data.stock_prices AS p JOIN stock_data.stocks AS s ON s.stock_code = p.stock_code WHERE p.trade_date >= DATE_SUB( (SELECT MAX(trade_date) FROM stock_data.stock_prices), INTERVAL 30 DAY ) ORDER BY s.company_name, p.trade_date;

8. 데이터 적재가 끝나면 Buffer Pool을 4GB로 다시 줄이기

16GB 설정은 적재 작업을 위한 임시 설정입니다. 데이터 검증까지 끝났으면 같은 SQL Editor에서 4GB로 되돌립니다.

-- 4 GiB = 4,294,967,296 bytes SET GLOBAL innodb_buffer_pool_size = 4294967296; SELECT ROUND(@@GLOBAL.innodb_buffer_pool_size / 1024 / 1024 / 1024, 2) AS buffer_pool_gb;
마지막 확인
결과가 약 4GB인지 확인합니다. 이 확인까지 해야 실습이 끝난 것입니다.
작업 전후 메모리 운영 원칙
평상시4GB
ERD 생성4GB 그대로 가능
적재 직전16GB 확대
SQL Import16GB 사용
검증 완료4GB 복구
Buffer Pool은 “크면 무조건 좋은 값”이 아니라 서버 전체 메모리와 다른 프로그램을 함께 고려해 운영해야 합니다.

9. 실습 중 자주 발생하는 오류

Forward Engineer에서 schema exists

동일 스키마가 이미 존재합니다. 기존 데이터를 지울지 판단하지 못했다면 DROP하지 말고 현재 DB를 먼저 확인합니다.

Access denied

Forward Engineering이나 SET GLOBAL 권한이 부족합니다. 로컬 실습에서는 root 또는 필요한 관리 권한이 있는 계정을 사용합니다.

SET GLOBAL 후 16GB가 안 됨

메모리 부족, chunk 단위 조정, 권한 문제를 확인합니다. 실제 값과 resize status를 다시 조회합니다.

Start Import 버튼이 비활성

Self-Contained File이 선택되었는지, SQL 파일 경로가 올바른지, 연결이 살아 있는지 확인합니다.

Table doesn't exist

데이터 Import 전에 Forward Engineering이 끝나지 않았거나 Target Schema가 잘못되었습니다.

Duplicate entry

이미 동일 PK 데이터가 들어 있을 수 있습니다. 같은 SQL을 두 번 적재한 것은 아닌지 먼저 확인합니다.

Cannot add/update child row

FK가 가리키는 부모 데이터가 먼저 존재해야 합니다. stocks와 stock_prices 적재 순서를 확인합니다.

Lost connection during query

대용량 SQL 실행 중 연결이 끊겼다면 Import Progress의 마지막 오류를 확인하고, 서버 상태·패킷 크기·타임아웃을 원인별로 점검합니다.

Buffer Pool resize 상태 확인

SELECT variable_name, variable_value FROM performance_schema.global_status WHERE LOWER(variable_name) LIKE 'innodb_buffer_pool_resize%';
