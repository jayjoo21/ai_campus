1. JOIN을 배우기 전에 전체 구조부터 보기

관계형 데이터베이스는 고객, 계좌, 거래, 카드, 결제, 대출처럼 성격이 다른 데이터를 여러 테이블로 나눠 저장합니다. JOIN은 이처럼 나눠진 정보를 공통된 키를 기준으로 다시 연결해서 하나의 조회 결과로 만드는 기능입니다.

고객 정보를 거래마다 반복 저장하지 않고, 고객·계좌·거래처럼 역할에 따라 나눈 뒤 ID로 연결합니다.

중복 감소

고객 이름과 지역을 거래 수천 건마다 반복 저장하지 않아도 됩니다.

일관성 유지

고객 정보가 바뀌면 고객 마스터 한 곳만 수정하면 됩니다.

업무 분리

거래, 카드, 대출, 모델 예측 등 서로 다른 업무 데이터를 독립적으로 관리할 수 있습니다.

JOIN을 한 문장으로
“기준 테이블의 한 행에 필요한 정보를 다른 테이블에서 찾아 옆으로 붙이는 작업”이라고 이해하면 됩니다.

2. ERD·JOIN에서 자주 만나는 핵심 용어

문법보다 먼저 용어를 이해하면 ERD와 JOIN이 훨씬 쉽게 읽힙니다. 아래 용어는 이후 데이터 분석·FDS·CSS·마이데이터에서도 계속 등장합니다.

ERDEntity Relationship Diagram

테이블과 테이블 사이 관계를 그림으로 표현한 설계도입니다.

Entity엔터티

관리하려는 대상입니다. 고객, 계좌, 거래, 카드처럼 테이블로 표현되는 경우가 많습니다.

Attribute속성

대상을 설명하는 값입니다. 고객의 지역, 결제의 금액, 거래일 등이 컬럼으로 표현됩니다.

PKPrimary Key

각 행을 유일하게 구분하는 키입니다. 같은 PK 값이 두 행에 존재하면 안 됩니다.

FKForeign Key

다른 테이블의 PK를 참조해 두 테이블의 관계를 만드는 키입니다.

Cardinality카디널리티

한쪽 행 하나가 다른 쪽 행 몇 개와 연결되는지 나타냅니다. 1:1, 1:N, N:M 등으로 표현합니다.

Grain그레인

한 행이 정확히 무엇을 의미하는지를 뜻합니다. 예: 고객 1명, 결제 1건, 종목×거래일 1건.

Referential Integrity참조 무결성

FK가 가리키는 부모 행이 실제로 존재하도록 관계의 일관성을 유지하는 원칙입니다.

Orphan Record고아 레코드

FK 값은 있는데 연결되는 부모 행이 없는 데이터입니다. 적재 누락이나 데이터 품질 문제를 의심합니다.

Fan-out팬아웃

1:N 관계를 여러 개 동시에 JOIN하면서 기준 행이 조합 수만큼 복제되는 현상입니다.

Point-in-Time시점 정합성

예측·판단 시점에 실제로 알 수 있었던 데이터만 사용하도록 맞추는 원칙입니다.

Master / Event마스터 / 이벤트

고객·가맹점처럼 비교적 안정적인 기준정보와, 결제·로그인처럼 시간에 따라 발생하는 사건 데이터를 구분하는 개념입니다.

Grain을 확인하는 가장 쉬운 질문
SQL을 작성하기 전에는 “기준 테이블의 한 행은 무엇인가?”, JOIN이나 GROUP BY 후에는 “최종 결과의 한 행은 무엇인가?”라고 확인합니다.

4. JOIN 전에 Grain부터 정하기

Grain은 “한 행이 무엇을 뜻하는가?”라는 정의입니다. JOIN 오류의 상당수는 문법이 틀려서가 아니라, 기준 Grain을 정하지 않은 상태에서 여러 테이블을 붙여 발생합니다.

업무기준 테이블기준 Grain한 행의 의미
주가 분석stock_pricesstock_code × trade_date특정 종목의 특정 거래일 가격 1건
FDScard_paymentspayment_id카드 결제 1건
CSSloan_applicationsapplication_id대출 신청 1건
마이데이터 추천campaign_experimentsexperiment_id특정 제안·실험 1건
Grain이 깨졌는지 확인하는 방법
JOIN 전100,000payment_id 100,000개
N:1 JOIN 후100,000정상적으로 Grain 유지
잘못된 1:N JOIN 후126,420같은 payment_id가 반복
결제 1건 = 1행이 목적이라면 JOIN 후에도 고유 payment_id 수와 전체 행 수가 같아야 합니다.
중요
행이 늘어났다고 정보가 더 풍부해진 것이 아닙니다. 같은 사건이 여러 번 복제된 것일 수 있으므로 SUM·AVG·COUNT 결과도 왜곡될 수 있습니다.

5. JOIN 문법을 구조로 이해하기

JOIN은 “어떤 테이블을 기준으로 시작해서, 어느 테이블의 어떤 정보를, 어떤 키로 붙일 것인가?”를 SQL로 표현한 것입니다.

SELECT
    기준테이블.컬럼,
    연결테이블.컬럼
FROM 기준테이블
JOIN 연결테이블
  ON 기준테이블.연결키 = 연결테이블.연결키
WHERE 조건;

6. INNER JOIN과 LEFT JOIN

둘의 핵심 차이는 오른쪽 테이블에 연결되는 행이 없을 때 왼쪽 기준 행을 남길 것인가입니다.

INNER JOIN

왼쪽
∩
오른쪽

양쪽 모두 매칭되는 행만 남깁니다. 매칭되지 않는 기준 행은 결과에서 사라집니다.

LEFT JOIN

왼쪽
전체
+
매칭값

왼쪽 기준 행은 모두 유지하고, 오른쪽에 매칭이 없으면 오른쪽 컬럼을 NULL로 표시합니다.

6-1. INNER JOIN 예

SELECT
    cp.payment_id,
    cp.customer_id,
    c.region,
    c.risk_segment
FROM card_payments AS cp
INNER JOIN customers AS c
  ON cp.customer_id = c.customer_id
ORDER BY cp.payment_at
LIMIT 100;

6-2. LEFT JOIN 예

SELECT
    cp.payment_id,
    cp.device_id,
    d.device_type,
    d.is_trusted
FROM card_payments AS cp
LEFT JOIN devices AS d
  ON cp.device_id = d.device_id
ORDER BY cp.payment_at
LIMIT 100;
LEFT JOIN에서 자주 발생하는 실수
아래처럼 오른쪽 테이블 컬럼을 WHERE에서 직접 제한하면 NULL 행이 제거되어 LEFT JOIN의 의미가 약해집니다.
-- 주의: 오른쪽에 매칭되지 않은 행이 제거됨
SELECT ...
FROM card_payments AS cp
LEFT JOIN devices AS d
  ON cp.device_id = d.device_id
WHERE d.is_trusted = 1;
판단 기준
“오른쪽 정보가 없어도 기준 행을 남겨야 하는가?”가 YES라면 LEFT JOIN을 먼저 고려합니다.

10. CSS와 Point-in-Time — 같은 고객의 여러 과거 보고서 중 무엇을 붙일까?

대출 신청과 외부 신용보고서는 단순히 고객 ID만 같다고 JOIN하면 안 됩니다. 한 고객에게 시간에 따라 여러 보고서가 존재하기 때문입니다.

Point-in-Time 개념

신청 전에 존재

신청 전에 존재
2025-05-15대출 신청
판단 기준시점

미래 정보 → 사용 금지
신청일 이전의 보고서만 후보이고, 그중 가장 최신 1건을 선택하는 것이 일반적인 Point-in-Time 원칙입니다.

    br.report_id,
    br.report_date,
    br.external_credit_score
FROM loan_applications AS la
LEFT JOIN bureau_reports AS br
  ON la.customer_id = br.customer_id
WHERE la.customer_id = 1
ORDER BY la.application_at, br.report_date;
문제
같은 application_id가 과거·미래의 여러 보고서와 연결되어 여러 행으로 반복될 수 있습니다.

10-2. 미래 보고서를 차단하면

SELECT
    la.application_id,
    la.application_at,
    br.report_id,
    br.report_date,
    br.external_credit_score
FROM loan_applications AS la
LEFT JOIN bureau_reports AS br
  ON la.customer_id = br.customer_id
 AND br.report_date <= DATE(la.application_at)
WHERE la.customer_id = 1
ORDER BY la.application_at, br.report_date DESC;
아직 남은 문제
신청일 이전 보고서가 여러 건이면 여전히 같은 신청이 여러 행으로 나옵니다. 최종적으로는 신청 시점 이전의 가장 최신 보고서 1건을 선택해야 Grain이 다시 application_id 1행으로 돌아옵니다.

11. Fan-out — 여러 1:N 테이블을 한꺼번에 붙일 때 행이 폭증하는 이유

Fan-out은 하나의 기준 행에 여러 자식 테이블을 동시에 JOIN하면서 가능한 조합이 만들어져 행이 크게 늘어나는 현상입니다.

고객 1명에게 여러 자식 데이터가 있을 때
accounts계좌 2개
transactions거래 10건
cards카드 3개
가능한 조합 수
2 × 10 × 3 = 60행. 단순 합인 15행이 아닙니다.
SELECT
    c.customer_id,
    a.account_id,
    t.transaction_id,
    ca.card_id
FROM customers AS c
LEFT JOIN accounts AS a
  ON c.customer_id = a.customer_id
LEFT JOIN transactions AS t
  ON c.customer_id = t.customer_id
LEFT JOIN cards AS ca
  ON c.customer_id = ca.customer_id
WHERE c.customer_id = 1;
왜 위험할까?
같은 거래가 계좌·카드 조합에 따라 반복되므로 SUM(t.amount)를 계산하면 실제보다 훨씬 크게 합산될 수 있습니다.

12. Fan-out을 막는 가장 기본적인 방법 — 먼저 집계한 뒤 JOIN

최종 Grain이 고객 1명이라면 거래 테이블을 그대로 붙이지 말고, 고객별로 먼저 요약해서 1행으로 만든 뒤 고객 테이블에 붙이는 방식이 안전합니다.

사전 집계(Pre-aggregation) 구조
transactions고객별 여러 거래
→
GROUP BY customer_id고객별 1행 요약
→
customersN:1 형태로 안전하게 JOIN
SELECT
    c.customer_id,
    c.region,
    tx.transaction_count,
    tx.total_amount
FROM customers AS c
LEFT JOIN (
    SELECT
        customer_id,
        COUNT(*) AS transaction_count,
        SUM(amount) AS total_amount
    FROM transactions
    GROUP BY customer_id
) AS tx
  ON c.customer_id = tx.customer_id;
결과 Grain
고객 1명 = 1행. 거래 여러 건은 JOIN 전에 고객 단위로 먼저 요약되었습니다.

13. JOIN 결과를 반드시 검증하는 방법

SQL이 오류 없이 실행되었다고 JOIN이 올바른 것은 아닙니다. 문법 검증과 데이터 의미 검증은 별개입니다.

JOIN 전 기준 행 수를 알고 있는가?
JOIN 후 전체 행 수가 예상과 맞는가?
기준 PK의 고유 개수가 유지되는가?
오른쪽 연결키가 실제로 유일한가?
매칭되지 않은 FK가 얼마나 되는가?
NULL이 생긴 이유를 설명할 수 있는가?

13-1. 전체 행 수와 고유 payment_id 비교

SELECT
    COUNT(*) AS joined_rows,
    COUNT(DISTINCT cp.payment_id) AS distinct_payments
FROM card_payments AS cp
LEFT JOIN merchants AS m
  ON cp.merchant_id = m.merchant_id
LEFT JOIN devices AS d
  ON cp.device_id = d.device_id
LEFT JOIN customers AS c
  ON cp.customer_id = c.customer_id;
결제 Grain을 유지한다면
joined_rows = distinct_payments가 되어야 합니다.

13-2. 마스터 키 중복 확인

SELECT
    merchant_id,
    COUNT(*) AS rows
FROM merchants
GROUP BY merchant_id
HAVING COUNT(*) > 1;

13-3. 연결되지 않는 FK 찾기

SELECT COUNT(*) AS unmatched_merchants
FROM card_payments AS cp
LEFT JOIN merchants AS m
  ON cp.merchant_id = m.merchant_id
WHERE m.merchant_id IS NULL;
Orphan Record
위 결과가 0보다 크면 결제에는 merchant_id가 있지만 merchants에 대응되는 행이 없는 데이터가 존재한다는 뜻입니다.

15. 확인 문제

문제 1 — stock_prices에 stocks 정보를 붙였을 때 결과 Grain은 무엇인가?

답: stock_code × trade_date입니다. stocks가 종목당 1행이면 주가 행 수는 늘어나지 않습니다.

문제 2 — card_payments를 기준으로 customers를 붙이는 관계는 결제 관점에서 N:1인가, 1:N인가?

답: N:1입니다. 여러 결제 행이 고객 한 행을 참조합니다.

문제 3 — LEFT JOIN 후 오른쪽 컬럼이 NULL인 것은 항상 데이터 오류인가?

답: 아닙니다. 기준 행은 존재하지만 오른쪽에 연결정보가 없을 수 있습니다. nullable FK라면 정상적인 상황일 수도 있습니다.

문제 4 — 고객 1명에 계좌 2개, 거래 10건, 카드 3개가 있을 때 세 테이블을 동시에 JOIN하면 왜 60행까지 늘어날 수 있는가?

답: 각 자식 테이블의 가능한 조합이 만들어지는 Fan-out 때문입니다. 2 × 10 × 3 = 60개의 조합이 생성될 수 있습니다.

문제 5 — 대출 신청일 이후의 신용보고서를 Feature로 사용하면 왜 문제가 되는가?

답: 신청 당시에는 알 수 없었던 미래 정보이므로 Data Leakage가 됩니다. Point-in-Time 원칙을 적용해야 합니다.

문제 6 — joined_rows와 distinct_payments가 다르면 무엇을 의심해야 하는가?

답: 같은 payment_id가 여러 행으로 복제된 것입니다. 오른쪽 테이블 키의 중복 또는 예상하지 못한 1:N 관계를 확인해야 합니다.
