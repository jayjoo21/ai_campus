1. SQL에서 데이터를 꺼내는 목적부터 이해하기

데이터 추출은 “테이블에서 컬럼 몇 개를 SELECT하는 작업”이 아닙니다. 먼저 어떤 분석을 할 것인지를 정하고, 그 분석이 요구하는 한 행의 단위와 시점, 필요한 원천정보를 정의한 뒤 SQL을 작성합니다.

SQL → Python 분석의 전체 흐름
DB
DB 원천분석 목적에 맞는 테이블을 선택합니다.
예: customers, card_payments, stock_prices
SQL
SQL 추출기간, 컬럼, JOIN, 기준시점, Grain을 정해 필요한 데이터만 정확히 꺼냅니다.
DF
DataFrame중복, NULL, 타입, 정렬을 검증한 뒤 Python에서 쓰기 좋은 형태로 받습니다.
PY
Python 분석Feature 생성, 통계 분석, 모델 학습, 시각화, 리포트 작성을 이어서 수행합니다.
SQL은 분석용 원천 데이터를 정확하게 준비하는 단계이고, Python은 그 데이터를 계산·모델링·시각화로 확장하는 단계입니다.

SQL의 역할

원천 선택, 행·컬럼 제한, JOIN 관계 확인, 시점 조건 적용, 중복·Grain 검증, 안전한 데이터 전달.

Python의 역할

수익률, rolling, WOE/IV, 스케일링, 머신러닝, Chunking, Embedding, 시각화 등 분석 계산.

중요한 질문

“이 값은 판단 시점에 존재했는가?”, “결과 한 행은 무엇인가?”, “Target이나 사후정보가 Feature에 섞이지 않았는가?”

핵심 원칙
SQL에서 많이 계산하는 것이 목표가 아닙니다. 분석의 의미를 깨뜨리지 않는 원천 데이터를 재현 가능하게 전달하는 것이 목표입니다.

2. 데이터 추출에서 반드시 알아야 할 용어

Raw Data원천 데이터

파생계산 전 DB에 저장되어 있는 기본 기록입니다. 결제금액, 거래시각, 종가 등이 예입니다.

Grain한 행의 단위

결과 한 행이 무엇을 의미하는지 정의합니다. 예: 결제 1건, 신청 1건, 종목×거래일 1건.

Feature입력 변수

모델이 예측에 사용하는 값입니다. 원천 컬럼일 수도 있고 Python에서 만든 파생변수일 수도 있습니다.

Target정답

모델이 맞히려는 결과입니다. FDS의 fraud_label, CSS의 default_12m_label 등이 이에 해당합니다.

Filter / Cohort분석 대상 조건

학습·분석에 포함할 행을 정하는 조건입니다. Feature와 역할이 다릅니다.

Master Data기준정보

고객·가맹점·종목처럼 다른 이벤트 행을 설명하는 비교적 안정적인 정보입니다.

Point-in-Time시점 정합성

판단 시점 이후에 생성된 미래정보를 사용하지 않는 원칙입니다.

Snapshot특정 시점 상태

어떤 기준시점의 고객 상태를 한 행으로 정리한 데이터입니다.

Data Leakage정보 누수

미래정보·사후판정·Target과 지나치게 가까운 정보를 Feature에 포함하는 오류입니다.

Corpus문서 집합

RAG에서 검색 대상으로 사용할 문서 전체 집합입니다.

Metadata문서 설명정보

문서 본문 외에 날짜, 유형, 출처, 버전 등을 설명하는 정보입니다.

Handoff분석 전달 단계

SQL에서 준비한 결과를 Python DataFrame으로 넘기고 분석을 이어가는 경계입니다.

4-3. 가격 + 종목 Master 결합

이 쿼리를 작성하는 목적
무엇을 얻으려는가?

삼성전자 시계열에 회사명·시장·업종을 붙여 분석에서 바로 식별 가능한 입력 구조를 만듭니다.

Python에서 이어지는 작업

가격 파생변수와 종목 단위 분석

USE stock_data;
-- [목적] 주가 시계열에 회사명·시장·업종을 붙여 Notebook 입력을 만듭니다.
SELECT
    p.stock_code,
    s.company_name,
    s.market,
    s.industry,
    p.trade_date,
    p.open_price,
    p.high_price,
    p.low_price,
    p.close_price,
    p.volume,
    p.change_rate
FROM stock_prices AS p
INNER JOIN stocks AS s
  ON s.stock_code = p.stock_code
WHERE p.stock_code = '005930'
ORDER BY p.trade_date;

날짜 정렬이 틀리면 전일수익률과 rolling 계산이 잘못되고, 같은 종목·거래일이 중복되면 지표가 왜곡됩니다.

5. CSS Notebook — 대출 신청 당시의 정보만 사용하기

CSS(Credit Scoring System)는 대출 신청이 발생한 시점에 알 수 있었던 정보만 사용해 향후 부실위험을 분석합니다. 따라서 서로 Grain과 시간축이 다른 신청·고객·신용보고서를 무작정 한 SQL에서 JOIN하지 않습니다.

왜 SQL에서 단순 JOIN하지 않는가?

Python에서 이어지는 작업

net flow, 세그먼트, Propensity, Next-Best-Action 계산

USE fintech_fraud_lab_class;
-- [목적] assigned_at 기준 과거 90일 거래건수를 experiment별로 집계합니다.
WITH ce AS (
    SELECT
        experiment_id,
        customer_id,
        assigned_at
    FROM campaign_experiments
),
txn AS (
    SELECT
        ce.experiment_id,
        COUNT(t.transaction_id) AS `txn_90d`
    FROM ce
    LEFT JOIN transactions AS t
      ON t.customer_id = ce.customer_id
     AND t.transaction_at < ce.assigned_at
     AND t.transaction_at >= DATE_SUB(ce.assigned_at, INTERVAL 90 DAY)
    GROUP BY ce.experiment_id
)
SELECT
    ce.experiment_id,
    ce.customer_id,
    ce.assigned_at,
    COALESCE(txn.txn_90d, 0) AS `txn_90d`
FROM ce
LEFT JOIN txn
  ON txn.experiment_id = ce.experiment_id
ORDER BY ce.assigned_at;

공통 RAG Corpus

-- [목적] 정책·상품·뉴스 문서를 같은 컬럼 구조로 맞춰 RAG Corpus를 만듭니다.
(SELECT
    'POLICY' AS `source_type`,
    CAST(doc_id AS CHAR) AS `source_id`,
    title,
    body_text,
    CAST(effective_date AS DATETIME) AS `doc_date`,
    doc_type AS `category`,
    version AS `extra_meta`
 FROM financial_policy_docs
 WHERE is_current = 1
   AND pii_level <> 'HIGH'
 LIMIT 3000)
UNION ALL
(SELECT
    'PRODUCT',
    CAST(product_doc_id AS CHAR),
    title,
    body_text,
    updated_at,
    product_type,
    product_name
 FROM product_documents
 LIMIT 3000)
UNION ALL
(SELECT
    'NEWS',
    CAST(news_id AS CHAR),
    title,
    body_text,
    published_at,
    topic,
    source_name
 FROM news_documents
 WHERE pii_level IN ('NONE', 'LOW')
 LIMIT 3000);

테이블 구조를 처음 확인하는 탐색 단계에서는 사용할 수 있지만, 실제 분석 Loader에서는 필요한 컬럼을 명시하는 편이 데이터량·개인정보 노출·스키마 변경 위험을 줄일 수 있습니다.

10. Python으로 넘기기 전 최종 검증

SQL이 실행된다는 사실만으로 분석 데이터가 올바른 것은 아닙니다. 잘못된 Grain이나 미래정보가 들어가도 Python 코드는 정상적으로 실행될 수 있기 때문에 전달 직전에 구조를 확인해야 합니다.

결과 한 행의 Grain이 분석 목적과 맞는가?
기준 PK가 예상치 않게 중복되지 않는가?
기준시점 이후의 미래정보가 들어오지 않았는가?
Target·사후판정 컬럼이 Feature에 섞이지 않았는가?
분석하려는 기간만 포함되어 있는가?
시계열은 필요한 순서로 정렬되어 있는가?
JOIN 전후 행 수가 예상과 맞는가?
NULL이 ‘정보 없음’인지 ‘오류’인지 구분했는가?
Python에서 만들 Feature를 SQL에서 중복 계산하지 않았는가?
데이터량이 크다면 기간·LIMIT·chunksize 전략이 필요한가?
마지막 한 문장
좋은 Loader는 “데이터를 많이 가져오는 코드”가 아니라 분석 시점에 실제로 사용할 수 있는 데이터를 정확한 한 행 단위로 재현하는 코드입니다.
